# OpenDraft UI Plan

Goal: a solid, good-looking UI foundation for a 2D-only CAD app, built on **egui/eframe** (the same approach as EffectCraft). This is a fresh start: the PySide6 app is a source of feature ideas only, not an architecture or look to copy.

## Requirements

- **Cross-platform: Windows and Linux are mandatory** (macOS nice-to-have, not a target yet). See "Cross-platform" below.
- **Ribbon toolbar** at the top (tabs, groups, large/small buttons), traditional Office/AutoCAD style.
- **Dockable window system**: Properties, Layers, etc. as panels that can be tabbed, split, rearranged, and floated.
- A modern, polished look (custom theme, real icons), not default egui styling.

## Visual style: dark, flat, Adobe-like

Reference: Adobe's "New Document" dialog (dark, flat, minimal chrome). Observations to turn into theme tokens in Phase 2:

- **Surfaces in layers of dark gray**, not black: window/background ~`#1E1E1E`-`#2B2B2B`, panels slightly lighter, input fields slightly darker or lighter than their panel. Depth comes from tone, not shadows or gradients.
- **One accent color: a saturated blue** (~`#1473E6`) used for primary buttons (Create), selection outlines (dashed/solid blue border on the selected preset), active toggles, and focus rings. No other accent colors in chrome.
- **Text hierarchy:** white/near-white for primary text; mid-gray for secondary labels, section headers, and hint text; small ALL-CAPS gray section headers (e.g. `PRESET DETAILS`).
- **Flat controls:** inputs and dropdowns are rounded rectangles (~4px) with a subtle 1px border or fill difference, no bevels. Dropdowns show a chevron on the right. Secondary buttons are outlined (pill/rounded border, transparent fill); the primary button is filled blue.
- **Tabs:** plain text with a white underline on the active tab; inactive tabs gray. This also suits the ribbon tab strip.
- **Generous spacing:** consistent 8px grid, ~16-24px padding around groups, clear separation between sections.
- **Thin, minimal scrollbars** that blend into the panel.
- **Line icons:** simple monochrome outline icons (~1.5px stroke) that tint to match text color.

Implementation notes:
- Define all of the above as a `Theme` struct (colors, radii, spacing, font sizes) in `od-ui`, converted to `egui::Visuals`/`Style` in one place. No hard-coded colors in widgets.
- Bundle one clean sans-serif UI font (e.g. Inter or Source Sans, which is close to Adobe Clean) with `include_bytes!` for identical rendering on Windows and Linux.
- Use a single SVG icon set with consistent stroke weight (e.g. Lucide or Phosphor, both permissively licensed); tint at render time.
- Custom-paint what egui's defaults can't match: the active-tab underline, the dashed selection border, outlined/filled buttons, thin scrollbars.
- Dark-only for v1; because everything flows through `Theme`, a light theme can be added later.

## Principles

1. **Layered crates; nothing below the UI knows about the UI.** Geometry and document logic must compile and be testable with no window.
2. **Every user action is a command.** Menus, toolbar buttons, shortcuts, and canvas tools all invoke named commands through one registry. This gives undo/redo, shortcut rebinding, a command palette, and scripting/testing for free.
3. **egui for chrome, custom painting for the canvas.** Panels, menus, dialogs, and property editors use egui widgets. The drawing viewport is a custom-painted widget with its own camera and tools.
4. **Stable widget ids.** Give interactive widgets explicit, stable ids (`ui.push_id`, `Id::new("...")`) so they can be driven by automated tests later.
5. **Wrap, don't fork.** Build small OpenDraft widgets (number field with units, property row, icon button) on top of egui rather than replacing it. If egui becomes limiting, these wrappers are the seam where a widget can be swapped.

## Target workspace layout

```
OpenDraft/
  Cargo.toml                 # [workspace]
  crates/
    od-core/                # geometry, entities, document model, units. No UI deps.
    od-commands/            # Command trait, registry, undo/redo stack, shortcuts map
    od-ui/                  # OpenDraft widgets + theme + panel/dock helpers (depends on egui)
    od-canvas/              # viewport: camera, grid, hit-testing, snapping, tools (egui painter)
    od-app/                 # eframe App, wires everything together (the binary)
```

Dependency direction: `od-app` -> `od-canvas`, `od-ui` -> `od-commands` -> `od-core`.

### Phase 2b: Ribbon (`od-ui::ribbon`)
egui has no ribbon, so this is a custom widget and the main UI-building task. Design:
- **Data-driven:** the ribbon is declared as data (tabs -> groups -> items), where each item references a command id from the registry. Label, icon, shortcut, and enabled state all come from the command, so nothing is defined twice.
- **Layout reference: Autodesk AutoCAD 2020 ribbon** (dark theme). Elements to mimic, top to bottom:
  1. **Title bar row:** app button at far left (a large square logo button that opens the application menu, like AutoCAD's "A"), then the **Quick Access Toolbar** (New, Open, Save, Save As, Plot/Print, Undo/Redo each with a dropdown arrow, plus a customize chevron), then the centered document title.
  2. **Tab strip:** plain text tabs (Home, Insert, Annotate, Parametric, View, Manage, Output, Add-ins, ...). The active tab has a lighter background that merges into the ribbon panel below it (no underline here; this is the AutoCAD convention and overrides the underline style used for dialog tabs).
  3. **Ribbon body:** a medium-gray-blue panel (lighter than the canvas) holding **panels** (AutoCAD's term for groups) separated by thin vertical dividers.
  4. **Panel title bar:** each panel has its name centered along the bottom (e.g. `Block`, `Layers`), with a small dropdown arrow when the panel can **expand** to show extra rows or a slide-out.
  5. **Item layout inside a panel:**
     - **Large buttons:** big icon on top, 2-line centered label below (e.g. "Create Block", "Layer Properties"). Some have a small dropdown arrow beside the label (split button).
     - **Small button stacks:** 2-3 rows of icon + text labels (e.g. "Recognize SHX Text", "Match Layer").
     - **Icon-only small buttons** in a compact grid (the Layers panel's icon rows).
     - **Combo box** spanning the panel width (the layer selector with its inline toggle icons) at the top of a panel.
     - Large and small items can mix in one panel; a panel is laid out as left-to-right columns.
  6. **Document tabs row** below the ribbon: `Start` and `Drawing1` tabs (with close x) and a `+` button for a new drawing.
  7. **Viewport label** overlaid at the canvas's top-left (`[-][Top][2D Wireframe]` style: clickable viewport controls).
- Structure: tab strip (Home, Draw, Modify, Annotate, View...), panels with a title and an optional expand arrow / dialog-launcher button, and an application-menu button.
- **Panel layout model:** a panel is a list of **columns**; each column is a large button, or a stack of 1-3 small items, or a wide widget (combo box). Responsive collapse works per panel, as below.
- **Item kinds:** large button (icon over label), small button (icon + label in a 3-row stack), toggle, dropdown/split button, combo box, and gallery (e.g. line types).
- **Responsive collapse:** when the window is narrow, groups shrink in stages (large -> small -> icon-only -> a single overflow dropdown). Needs a layout pass that measures group widths.
- **Contextual tabs** that appear based on selection or active tool (e.g. a "Text" tab when text is selected).
- **Quick access toolbar** (save, undo, redo) and ribbon minimize/pin.
- **Keyboard access:** Alt-key hints on tabs and items (optional, later).
- Custom painting (`Painter`) for tab and group chrome so the look is consistent; egui widgets inside groups.
- **Done when:** a ribbon with 3 tabs and several groups renders from a data definition, collapses gracefully when the window narrows, and its buttons fire registry commands.

### Phase 3: Command system (`od-commands`)
- `Command` trait / struct: id (`"file.open"`), label, default shortcut, enabled predicate, execute.
- Registry; shortcut handling in one place per frame; menus and toolbar are generated from the registry.
- Undo/redo: command stack with an `Action` that can `do` and `undo` against the document. Start with a snapshot or inverse-op model; decide in this phase.
- **Done when:** File/Edit menu items, toolbar buttons, and shortcuts all trigger the same commands; Ctrl+Z / Ctrl+Y work on a trivial test action.

### Phase 4: Docking and layout
- Use **`egui_dock`**: panels as tabs, drag to rearrange, split left/right/top/bottom, and float. The canvas is a dock tab too (so it can be split into multiple views later).
- Define a `Panel` trait in `od-ui` (id, title, icon, `ui()`); Properties, Layers, Command Line, etc. implement it. A View menu/ribbon button re-opens closed panels.
- Persist the dock layout, window size/position, and recent files (eframe storage; config dir via the `directories` crate).
- Provide a "Reset layout" command and a few built-in layout presets.
- **Known limit:** floating panels are in-app windows inside the main window, not separate OS windows. That works the same on Windows and Linux, but dragging a panel onto a second monitor is not supported. Real multi-window docking (egui's multi-viewport support) is possible later but is a rough edge, so treat it as a stretch goal.
- **Done when:** the user can rearrange, float, close and re-open panels, and the layout survives restart.

## Cross-platform (Windows + Linux)

- **Backend:** eframe uses `winit`, which handles Windows, X11 and Wayland. Pick the renderer (`glow` OpenGL vs `wgpu`) in Phase 1 and test it on both; `wgpu` is the better long-term choice for a custom canvas but needs a Vulkan/GL-capable driver on Linux.
- **Test early on real Linux** (a VM or WSL2 with WSLg is enough to start; also check both X11 and Wayland). Don't leave this until the end.
- **Linux build dependencies** (X11/Wayland/xkbcommon/GL dev packages) documented in the README and installed in CI.
- **Shortcuts:** store them as `Cmd/Ctrl`-style logical modifiers (egui's `Modifiers::COMMAND`) so macOS works later with no changes.
- **Paths and files:** use the `directories` crate for config/data dirs and `rfd` for native file dialogs; never hard-code path separators.
- **Fonts:** bundle the UI font and icons in the binary (`include_bytes!`) so the app looks identical on both OSes, instead of depending on system fonts.
- **Packaging (later):** Windows installer/zip, Linux AppImage or Flatpak.
- No platform-specific code unless wrapped in `cfg(target_os = ...)` behind a small `platform` module.

## Early risks

| Risk | Mitigation |
|---|---|
| egui canvas too slow for large drawings | Benchmark in Phase 5; fall back to an `egui_wgpu` custom callback for the canvas only |
| egui immediate-mode state gets messy | Keep all state in the document and commands; widgets only read and emit commands |
| Text input quirks (IME, complex editing) | Rely on egui's `TextEdit`; do not write a custom text editor |
| Docking needs exceed egui | Wrap panel code behind `od-ui` helpers so the dock library can change |

## Autosave and crash recovery (done)
Settings > Files: recovery copies every Off / 1 / 2 / 5 / 10 minutes (default 2). Each drawing with unsaved changes gets a copy in this run's session folder; saving, closing or undoing back to clean removes it; a normal exit deletes the folder. After a crash or kill, the next start offers "Recover drawings" (Recover / Discard; closing the dialog keeps them for next time). A lock file per running instance tells a crash from another copy that is still running. Recovered drawings open as unsaved. Tested for real: drew, waited for the autosave, killed the process, relaunched, recovered.

## Audit of 11-10-2026 (independent review; notes in `AUDIT (11-10-2026).md`)
No critical findings; structure judged good for this stage. Seven findings, and what was done:
1. **Document invariants (Major): partly done.** `Document::validate()` (`od-core/src/validate.rs`) checks unique ids and names, layer 0, objects on real layers, the current layer and the counters. `Session` runs it after every edit, transaction, undo and redo in debug builds and tests; the native writer refuses an invalid drawing. Still to do: make `push`/`insert`/`push_layer`/`replace_attrs` return `Result` so release builds reject a bad edit at the call, with undo and redo using separate restore-only methods.
2. **Commands not modal (Major): done.** `Command::transparent()` plus `Registry::busy_when`: while a command runs only transparent commands are enabled; panel edits and undo end the running command first. See ARCHITECTURE.md, "A running command owns the drawing". Still to do: finer flags if needed, and Ctrl+Z inside a command routed to the command's own Undo option.
3. **Runner jobs not panic-contained (Major): done for jobs.** `Request::Run` jobs run under `catch_unwind` and end the command as `Crashed`. Not done: a bounded join on drop (the thread ends when its reply channel closes) and a data-only `Request::Run` for plugins (plugins are out of process anyway).
4. **File I/O on the UI thread (Major): done.** Open, save, export and autosave run on a worker thread (`io.rs`, `file_io.rs`) from copies of the drawing and are applied on the UI thread when finished; the unsaved-changes question waits for the save, the window waits for writes before closing, edits made during a save stay unsaved, and an autosave pass is skipped while the last is still writing. Checked in the real app with a 139 MB, 400,000-line drawing: the window stayed responsive while it loaded. Cancel for a stalled open, save or export is also done: a Cancel button in the status bar after one second (and Esc) abandons the job, discards its result, and a cancelled save never replaces the file. Still to do: a progress bar rather than a status message, loading crash-recovery files in the background, and writing large `.odx` files more compactly (see Files, "compressing large drawings").
5. **Atomic save temp file (Major): done.** Unique, exclusively created temp name per save, cleanup only of that file, sync of the file and (Unix) the folder; tests cover a user's own `name.odx.tmp` surviving a failed save.
6. **Unknown entity policy (Major): decided and documented.** Refuse, never skip: a new entity kind bumps the format version. Test renamed to say so; comments in `native.rs` fixed.
7. **File sizes (Minor): partly a miscount.** The rule counts production code; the audit's totals included tests (`files.rs` is about 375 production lines). Really over: `widgets.rs` (754), `view.rs` (591, now split: painting is in `view/paint.rs`), `dxf/read.rs` (442). A test (`od-app/tests/file_sizes.rs`) now fails on any file over 450 and lets those three shrink but not grow. To do: split `widgets.rs` by widget family, `view.rs` into input, painting and prompt overlay, `dxf/read.rs` into tokenizer, layers and entities.

## Arc (done)
`draw.arc` (A, ARC): start point, second point, end point (an arc through three points), or by the Center option start, center, end (counter-clockwise from the start to the direction of the end point; the radius comes from the start point). The ghost previews the arc, points in a line are refused and asked again. `Entity::Arc { center, radius, start, end }` runs counter-clockwise in radians, like DXF; `od_core::arc` holds the pure geometry (sweep, containment, bounds, distance, flattening, circle through three points) used by drawing, hit-testing, selection, snapping (endpoints, midpoint, center), the Properties panel (center, radius, start and end angle in degrees, length) and Move, Copy, Rotate, Mirror and Scale. A mirrored arc swaps its ends so it still runs counter-clockwise. Files: `.odx` is now version 2 (version 1 files still open); DXF ARC is read and written natively, so arcs round-trip. Arcs render as straight pieces within half a pixel of the curve. The ribbon icon is Lucide's rainbow, as the set has no arc.

## Grips (design notes; built, see "Grips, done" below)
Select an object and edit it by dragging its grip points, as in AutoCAD. Each kind offers grips at its defining points: line (both ends and the midpoint), circle (center and four quadrants), arc (ends, midpoint, center), rectangle (corners and edge midpoints), polyline (vertices and segment midpoints). Click a grip to make it hot, then move it (a ghost shows the result) and click to place, with snaps and typed coordinates as in other commands; Esc cancels. An end or vertex grip stretches, a midpoint or center grip moves the whole object, and a quadrant or radius grip resizes. Shift-click adds grips to a multiple stretch.
Design notes: grips are pure data per entity (`grips(entity) -> Vec<Grip>` and `with_grip_moved(entity, index, to) -> Entity`, tested like `properties.rs`), so the canvas only draws and hit-tests them. The edit goes through the normal transaction, so it is one undo step. Grips show only for selected objects, never on locked layers, and not while another command runs. This also unblocks Stretch. A rectangle dragged by one corner stays a rectangle; dragging an edge midpoint moves that edge.

## Geometry core (done)
Pure functions in `od-core`, the base for Trim, Extend, Break, Fillet, Chamfer and Offset; no UI and no document.
- `intersect.rs`: `Entity::curves()` breaks any entity into `Curve`s (segment, circle, arc); `Entity::intersections(other)` gives every crossing without repeats (a shared polyline corner counts once); `Entity::nearest_point(p)` and `distance_to(p)`; `Curve::extended_intersections` meets the whole line or circle a curve lies on with another curve (how far could it go). Collinear segments and equal circles overlap everywhere and report no single crossing, by design.
- `split.rs`: `Entity::split_at(points)` cuts a line, arc, circle, rectangle or polyline at points on it and returns the pieces in order (lines, arcs or open polylines). Cuts at the ends and repeats are ignored; a circle needs two cuts; a closed path cut once opens at the cut. Trim is "split at the cutting edges' crossings, drop the piece nearest the click"; Break is a split at two points.
- `extend.rs`: `Entity::extended_to(End::Start | End::End, boundaries)` lengthens a line (along its direction), an arc (round its circle, never past a full turn) or the end segment of an open polyline to the nearest boundary point ahead of the tip. The boundary has to exist where it is met (no implied extension of the boundary; an "Edge extend" option can come later).
- Tests include randomized checks: every crossing lies on both outlines and is found either way round, the nearest point is on the outline and beaten by no sample, and cutting never changes total length.
Still to do: tangent points and fillets between curves, offset curves, and moving `od-canvas`'s hit-testing onto `Entity::distance_to` (it keeps its own faster copy for now, since picking tests every entity each frame).

## Trim (done)
`modify.trim` (TR, TRIM) follows AutoCAD: select cutting edges, or press Enter to use every visible object; then click the part of each object to remove. The clicked piece (the one nearest the click, between the crossings) is cut away. A line keeps its identity for the first remaining piece and any others are new objects on the same layer and attributes; a circle becomes an arc; a rectangle becomes polylines. Each trim is one undo step and the Undo option takes back the last one; Enter or Esc ends. Messages say when an object crosses no edge or cannot be divided (a circle cut once, a cut at an end). Locked and hidden layers are not offered for trimming. The logic is `trim::trim_plan(target, cutters, at)`, pure and tested; it uses the geometry core.
New prompt machinery that other commands can use: `Wants::Object` / `Editor::ask_object` (click one object, answered with the object and the clicked point; the canvas skips snapping and highlights the object under the pointer) and `Options::allow_empty` / `Editor::ask_selection` (a selection prompt where Enter with nothing selected is an answer).
Still to do: Fence and Crossing selection of objects to trim, the Edge (extend the cutting edge) and Project options, and trimming polylines at their own crossings (an object is not its own cutting edge yet).

## Extend (done)
`modify.extend` (EX, EXTEND) shares Trim's code (`od-app/src/edges.rs`): select boundary edges or press Enter for every visible object, then click each object near the end to lengthen; it grows to the nearest boundary ahead of that end. Objects already selected when the command starts are the edges, and the first question is skipped. Shift-click does the other command's job in both: Shift while extending trims, Shift while trimming extends (the pick now carries Shift: `Editor::ask_object` answers with `Picked { id, at, shift }`). Lines, arcs (round their own circle, never past a full turn) and the end segment of open polylines extend; circles, rectangles and closed polylines say they cannot. A boundary has to exist where it is met, so there is no implied extension of the boundary yet (AutoCAD's Edge option). Messages: "No boundary in the way." and "Object cannot be extended." The Modify ribbon has an Extend button (arrow to a line).
Still to do: the Edge option, polyline arc segments, extending to a boundary that is itself extended, Fence and Crossing selection.

## Offset (done)
`modify.offset` (O, OFFSET), AutoCAD style: give a distance (or the Through option, or Erase to delete the source), then click an object and click the side the copy goes to; repeat until Enter or Esc. With Through, the distance is how far the clicked point is from the object. A ghost shows the copy while choosing the side. Each copy is one undo step and takes the source's layer and attributes. If no copy fits (an inward offset that uses up a circle, a rectangle squeezed flat, a click on the object itself, zero distance) the command line says so and asks for the next object.
Geometry: `Entity::offset(distance, toward)` in `od-core/src/offset.rs`, pure and tested. Lines move sideways; circles and arcs change radius; rectangles grow or shrink and stay rectangles; polylines move every segment to the chosen side (the same side of travel for all, whichever way it was drawn) and join neighbours at sharp corners, dropping segments an inward offset turns back on themselves.
Still to do: typed or picked distance by two points, the Multiple and Layer options, trimming the self-crossing loops an inward offset of a tight curve can leave (polylines have no arc segments yet), and the AutoCAD default of last-used distance.

## Fillet and Chamfer (first version, for two lines; superseded by "completed" below)
`modify.fillet` (FIL, FILLET) and `modify.chamfer` (CHA, CHAMFER): pick the first line, then the second. Fillet joins them with a tangent arc of the current radius; Chamfer with a straight line cut at two distances along the lines. Each line keeps the part on the side where it was picked, and is extended or cut back to the joint. Options: Radius (Fillet) or Distance (Chamfer), Trim (Trim or No trim: with No trim the lines stay and only the joint is added) and Multiple (carry on with more corners until Enter). Radius or distances of zero make the lines meet at their corner. The settings are remembered between uses, like AutoCAD's FILLETRAD, CHAMFERA, CHAMFERB and TRIMMODE (kept in memory only for now; they should become system variables saved with the drawing). The joint takes the first line's layer and attributes; the whole thing is one undo step. Messages: the lines are parallel, only lines can be joined for now, the radius or distance is too large, select a different line.
Geometry: `fillet_lines` and `chamfer_lines` in `od-core/src/corner.rs`, pure and tested (tangent points, centre on the bisector, the short arc counter-clockwise, extension and trimming from either line direction).
Still to do: fillet between arcs and circles and a line, the Polyline option (fillet every vertex), Fillet and Chamfer of polyline segments, the Angle and Method options of Chamfer, Shift-click for a zero-radius corner, and FILLETRAD and friends as real system variables.

## Fillet and Chamfer, completed
Fillet now works between any two of line, arc and circle (`od-core/src/fillet.rs`): the arc is the circle of the given radius that touches both, found by moving each curve sideways by the radius and meeting the results; of the several candidates the one whose touching points are nearest the picks wins. Each curve keeps the side where it was picked and is cut or extended to its touching point; a circle is never trimmed; a radius larger than the lines extends them to the arc. Radius 0 joins the curves at their crossing. Chamfer works on lines and has two methods: two distances, or a length along the first line and an angle (`Chamfer::Distances` and `Chamfer::Angle`, `corner.rs`). Both commands also join two segments of one polyline (click the two sides; they must meet at a vertex), and the Polyline option rounds or cuts every corner of a polyline or rectangle that fits (corners whose segments are too short are left sharp and counted) (`polycorner.rs`). A chamfer keeps the polyline whole. A fillet needs arc segments, which polylines do not have yet, so it replaces the polyline with its straight runs and the arcs as separate objects, in order, and says so. Holding Shift on the second pick joins at a sharp corner. Options: Radius, Distance, Angle, Polyline, Trim and Multiple.
The settings (`corner_memory.rs`) are real system variables, FILLETRAD, CHAMFERA, CHAMFERB, CHAMFERC, CHAMFERD (degrees), CHAMMODE (0 distances, 1 length and angle) and TRIMMODE, usable with SETVAR, and are saved with the user's settings. In AutoCAD they are saved in the drawing; here they are per user until drawing-saved variables exist.
Still to do (polyline arc segments are now done, so a fillet keeps a polyline whole): fillet of a line with a polyline end segment (AutoCAD joins them), parallel lines (AutoCAD draws a semicircle), and the Undo option inside Multiple.

## Grips, done
Selected objects show square grips (up to 100 objects at once); the one under the pointer lights up. Press a grip to edit it: it starts a command ("Stretch"), so the usual point prompt comes with it: the preview follows the pointer, snaps apply, typed coordinates are relative to the grip (`@0,5`), Esc cancels leaving the object selected, and the change is one undo step ("Stretch", "Move" or "Resize"). Pressing a grip does not change the selection, and nothing is picked or boxed from that press. Grips are hidden while another command runs, and objects on locked or hidden layers show none.
What each object offers (`Entity::grips`, `Entity::with_grip_moved` in `od-core/src/grip.rs`, pure and tested): line: both ends (stretch) and the middle (moves the line); circle: the centre (moves it) and the four quadrants (set the radius); arc: both ends and the middle (the arc is redrawn through the three points as dragged) and the centre (moves it); rectangle: the four corners (the opposite corner stays) and the four edge middles (the edge moves sideways); polyline: each vertex (stretch) and each segment's middle (moves that segment's two vertices, including the closing one).
More grip editing (added after the first version): Shift-press grips to pick several (they turn red, "warm", and stay picked across objects); pressing one of them makes them all hot and they stretch together by the same displacement, the pressed grip being the base point. Pressing a grip that is not warm edits just that one. Esc drops warm grips before it clears the selection. While editing, the options are Base point (measure from another point), Copy (leave the original and add an edited copy, again and again), Undo (take back the last copy) and eXit. Enter cycles the edit through Move, Rotate, Scale and Mirror of the whole objects whose grips are hot, about the base point, each with its own prompt and live preview; typed values work (an angle in degrees, a scale factor, a point). The copy option applies to every mode and each edit is one undo step.
Still to do: Space as well as Enter for cycling, stretching only the vertices inside a crossing window (Stretch command), polyline arc segments (so a dragged arc-segment grip can exist), and a grip for an arc's sweep angle (the middle grip currently reshapes the arc through three points). A rectangle with two hot corners moves them together but, being axis-aligned, cannot shear: the two top corners moved sideways shift the whole top and bottom together.

## Polylines with arc segments (done)
A polyline segment can be an arc. `Entity::Polyline` has `bulges: Vec<f64>`: empty when every segment is straight, otherwise one value per point, `bulges[i]` shaping the segment from point `i` to the next (the closing segment for the last point of a closed polyline). A bulge is the tangent of a quarter of the arc's angle, as in DXF group 42: 0 straight, positive counter-clockwise, negative clockwise, 1 a half circle. `od_core::bulge` holds the pure geometry (the arc of a segment, points along it, nearest point, length, area, flattening, bounds, the bulge through three points, tangent arcs, the bulge of a piece of an arc).
Everything that reads a polyline handles arcs: bounds, moving, rotating, scaling, mirroring (which flips every bulge), picking, window and crossing selection, snapping (endpoints, midpoints, and an arc segment's centre), drawing, the Properties panel (length and area include the arcs), intersections, splitting for Trim and Break (a piece of an arc keeps its circle, with its own bulge), Extend (the end segment, straight or arc), Offset (arc segments become concentric arcs, joined to their neighbours where the curves meet; an arc whose radius is used up vanishes), grips (the middle of an arc segment reshapes it through the dragged point) and DXF (bulges are read from LWPOLYLINE and POLYLINE vertices and written as group 42, so they round-trip, where they used to be flattened into short straight pieces).
The `.odx` format is version 3 (an optional `bulges` list, left out when every segment is straight; version 1 and 2 files still open). The Polyline command has an Arc option: arcs leave tangent to the segment before (east for the first), and Line goes back to straight segments; Close joins with an arc when arcs are on.
Fillet and Chamfer now keep a polyline whole. Filleting a vertex replaces it with two points joined by an arc segment (a chamfer, a straight one), so rounding a rectangle gives one polyline, not lines and arcs. A vertex next to an arc segment is left as it is.
Still to do: the Arc and Line options inside the Polyline command's other forms (Width, Halfwidth, Length, Second point, direction), fillet and chamfer of a vertex next to an arc segment, joining a line and an arc into a polyline (PEDIT Join and the JOIN command), exploding a polyline into lines and arcs, and offsetting tight arcs inward without the loops the join can leave.

## Join (done)
JOIN (alias J) takes the selected objects, or asks for some, and chains the lines, arcs and open polylines whose ends meet (within 1e-6) into one object; `od_core::join` holds the geometry. The result is a polyline with the arcs kept as bulges, except that lines on one line become a single line, arcs of one circle become one arc (or a circle when they close), and an open polyline whose ends meet is closed. The first object of each group keeps its layer and place in the drawing order; the rest are removed. One undo step.
Still to do: a Fuzz distance for ends that nearly meet, joining a rectangle or closed polyline (AutoCAD refuses these too), joining splines and ellipses (not yet drawable), and PEDIT Join (done, with its own chaining in `od_core::pedit`).

## Explode (done)
EXPLODE (alias X) takes the selected objects, or asks for some, and replaces each rectangle and polyline with its lines and arcs (`Entity::explode` in `od_core`; a bulged segment becomes an arc, zero-length segments are skipped). The pieces keep the object's layer and attributes. They end up selected, as in AutoCAD. Lines, circles and arcs are left alone. One undo step. The `F` alias now means Fillet and `CP` Copy, as in AutoCAD; Fence and CPolygon are typed in full.
Still to do: blocks and hatches (not yet drawable), and polyline width once it exists.

## Break (done)
BREAK (alias BR) asks for one object: the click that picks it is the first break point, then it asks for the second point, with a preview of what is left; the First point option re-specifies the first one. `Entity::break_between` in `od_core` moves both points onto the outline, cuts there with `split_at` and drops the piece between them. A line, arc or open polyline loses the part between the points, whichever comes first, and a second point past an end removes up to that end (both beyond the ends removes the object). A circle becomes an arc, losing the part counter-clockwise from the first point; a rectangle becomes an open polyline. The first piece keeps the object's identity and the rest are new objects with its attributes. Giving the same point twice (`@0,0`) divides the object in two without removing anything. One undo step.
Break always asks for its object, even with a selection, as in AutoCAD. Still to do: `@` alone as "same as the first point" (the command line does not read it), and Break at Point as a ribbon button.

## Stretch (done)
STRETCH (alias S) asks for a crossing window (two corners) or, with the CPolygon option, a crossing polygon; then a base point and a second point, with a preview. `Entity::stretched` in `od_core` moves the defining points inside the region and leaves the rest: a line moves the end inside; an arc moves an end and keeps the angle it turns through; a polyline moves its vertices and keeps every bulge; a circle moves whole when its centre is inside; a rectangle stays a rectangle when the corners moved keep its sides along the axes and otherwise becomes a closed polyline. An object with all its points inside just moves. `Region::contains` in `od-canvas` is the point-in-region test. One undo step.
Differences from AutoCAD: Stretch always asks for its own window and ignores any selection, so objects cannot be added by clicking or by Fence, and there is no Displacement option. A rectangle or arc handled by the grips keeps the grips' rules, which differ slightly.

## Dynamic Input (done, first implementation)

Cursor-local prompts and editable X/Y, coordinate-expression, distance, angle,
number and text fields share the existing Editor/Runner replies and command-line
echo. LINE uses separate distance, angle and prompt anchors; RECTANGLE uses
Cartesian fields. Tab/Shift+Tab lock and cycle fields, Down opens the compact
options menu, Enter submits, and Escape clears entry before cancelling. Snapped
and trailing cursor positions drive tooltips; typed locks constrain live ghosts
and clicks. Stable widget IDs preserve focus while moving. Edge placement uses
clamping, flipping and hysteresis; hovering a tooltip freezes its position for
mouse editing. Invalid entry cannot place a point or alter the relative origin.
Floating fields avoid a 56-point crosshair clearance zone, including short LINE
segments and viewport edges; numeric hover labels no longer obscure the cursor.

F12 taps toggle, holds temporarily suppress, and the DYN status toggle has a
context menu for Settings > Drafting. Settings persist pointer/dimensional input,
prompts, coordinate mode/format and visibility. AutoCAD variables implemented:
DYNMODE, DYNPROMPT, DYNPICOORDS, DYNPIFORMAT, DYNPIVIS. First-point coordinates
are absolute; later cursor coordinates are relative by default, with # and @
overrides. The command line retains its absolute defaults and keyboard ownership.
LINE now offers Undo immediately after the first point; undoing that first point
returns to the first-point prompt without undoing existing drawing objects.

Verified with parser/app tests and egui event tests, including 30 cursor-motion
frames during entry, typed input plus Enter in one frame, option-menu clicks,
locked coordinates/dimensions, rejected clicks and smaller viewports at 100%,
125% and 150% scale. The running app was checked for a 10-unit, 90-degree line.

Remaining AutoCAD parity work: entity-specific grip dimension fields and
DYNDIVIS/DYNDIGRIP, recent-input recall, tracking aids, and the dimension fields for the rectangle's Rotation. Existing
command options are shown without advertising unsupported operations.

Update: the fields now sit on ghost dimensions like AutoCAD's. A vector shows a linear dimension offset from the rubber band plus an angular arc from the zero direction, with the distance and angle boxes on them; a rectangle shows two orthogonal dimensions; a lone distance (circle radius) shows the linear one. Short vectors, absolute coordinates and prompts without a base keep the old row beside the cursor. Pure geometry with tests in `dynamic_input/dimensions.rs`.

## Command specification gaps closed (done; from `Command_specifications.md`)
Every option in the specification is now built, each as pure, tested geometry in `od-core` plus a command that only asks.
- **Move:** the Displacement option (and Enter at the base point prompt) takes a vector from the origin.
- **Scale, Rotate** (`scale_rotate.rs`, split out of `modify.rs`): Copy keeps the originals; Reference takes a reference length or angle (default 1 and 0) and a new one, either typed, picked from the base point, or by Points.
- **Circle** (`circle.rs`): 3P, 2P and Ttr. Ttr (`od_core::tangent_circle`) treats lines, circles, arcs and polyline segments as the whole line or circle, offsets both by the radius, and takes the crossing whose touching points are nearest the picks; "Circle does not exist." when none fits.
- **Arc** (`arc_cmd.rs`, maths in `od_core::arc_make`): Center first at the first prompt; second prompt Center or End; after Center the end point or Angle or chord Length; after End the centre, Angle, Direction or Radius. Counter-clockwise arcs as entities always are; a negative included angle runs clockwise, a negative radius or chord gives the longer arc.
- **Rectangle** (`rectangle.rs`, shape in `od_core::rect`): first-corner Chamfer, Fillet, Width, Elevation and Thickness (remembered in `rect_memory.rs`, saved with the settings, with system variables PLINEWID, ELEVATION and THICKNESS; elevation and thickness are 3D values this drawing keeps but does not draw). Area and Dimensions give a size and the pointer then picks the quadrant; Rotation turns the rectangle about the first corner (an angle or Pick points). A square, hairline, axis-aligned result is still a `Rectangle`; otherwise it is a closed polyline with arcs for fillets. Corners that do not fit are left square.
- **Polyline** (`polyline_cmd.rs`, `polyline_arc.rs`): Width, Halfwidth and Length, and in Arc mode Angle, CEnter, CLose, Direction, Halfwidth, Line, Radius, Second pt, Undo and Width. Polylines gained `widths` (see ARCHITECTURE.md), so `.odx` is now version 4 and DXF carries widths on the vertices (codes 40 and 41, read from POLYLINE and LWPOLYLINE, including the constant width 43; `dxf/read/polyline.rs`).
Known limits: the Arc included-angle prompts take a typed angle only (a click is ambiguous with a direction); Trim, Break, Join, Offset, Fillet, Chamfer and Explode drop widths; a wide polyline is picked and snapped on its centreline; Rectangle Area ignores the corner rounding; the Properties panel does not show widths yet.

## Layouts and viewports (done, phases 1-3 of `private_material/layouts_specification.md`)
Model/Layout tabs along the bottom of the drawing, as in AutoCAD. A layout is a sheet in millimetres holding rectangular viewports; each shows model space at a scale. Built on the existing model, not the specification's slotmap database: `Document::layouts` (a list of `Layout`, each with `Viewport`s, ids never reused), changed as a whole list by the undoable `SetLayouts` action. Plan views only: a viewport is a uniform scale and an offset, so `od_core::layout` holds the whole mapping (`model_to_paper`, `paper_to_model`, zoom and pan about a point) with round-trip tests.
- **Spaces.** `od_canvas::Space` is `Model`, `Paper(layout)` or `Viewport(layout, viewport)` and lives in each drawing's `View`. In `Viewport` the canvas camera is the sheet camera composed with the viewport, so picking, snapping, grips and ghosts work unchanged inside it and ignore the pointer outside its window. MSPACE/PSPACE (`MS`, `PS`) and double-clicking in or out of a viewport switch; no object ever moves. On the bare sheet drawing and modify commands are refused (they would land in the model at sheet coordinates); `MVIEW`, `LAYOUT` and `VPSCALE` work there.
- **Navigation.** Wheel and middle-drag over an unlocked active viewport change its view; elsewhere, or when it is locked, they move the sheet. Zoom Extents frames the sheet, or the model in an unlocked active viewport. Panning and zooming a viewport is stored in the drawing but is not an undo step, as in AutoCAD.
- **Commands.** `LAYOUT` (`LO`: New, Copy, Delete, Rename by name), `MVIEW` (`MV`: two corners; the viewport frames the drawing at a tidy scale), `VPSCALE` (`1:50`, `2:1`, `1/100`), `VPLOCK`, Erase removes a picked viewport (click its border on the sheet), and tab right-click offers New/Copy/Delete. New layouts are A4 landscape with one viewport.
- **Files.** `.odx` is now version 5 (layouts, with counters so ids stay retired); DXF export notes that layouts are not written and writes model space only.
- **Paper-space entities (done).** Every command that draws or edits works on the bare sheet, in millimetres: Line, Rectangle, Move, Trim and the rest, with snapping, picking, grips and undo. An `Object` carries `layout: Option<LayoutId>` (`None` is model space) in the same list and with the same ids; the document has an *active space* (`Document::set_active_layout`, set by `Doc::set_space`, not undoable or saved) that `visible_objects`, `selectable_objects`, `bounds`, `has_objects_here` and `AddEntity`/`AddCopies` follow. Viewports always show model space (`visible_in(None)`), and what is drawn on the sheet goes over them. Deleting a layout removes its sheet objects (one undo step) and Copy copies them. `.odx` stores an optional `layout` on an object (refused if that layout is missing). DXF export writes model space only (`model_objects`).
- **Page Setup (done).** `PAGESETUP` (Page Setup dialog, `app/page_setup_dialog.rs`): layout name (so layouts can be renamed), standard paper sizes, orientation, or a custom width and height in mm. One undo step through `AppState::set_page_setup`, which refuses an empty or duplicate name and a sheet under 10 mm. Viewports keep their places on the sheet when it is resized.
- **Per-viewport layer freeze (done).** `VPLAYER` (Freeze, Thaw, Reset; layer names separated by commas or `*`; Current or All viewports, All when none is picked) is one undo step. `Viewport::frozen` holds the layer ids; a frozen layer is not drawn, picked or snapped in that viewport, while model space and other viewports still show it. The document's `active_frozen` (set every frame by `Doc::keep_space_valid`) applies it to the object queries while working through a viewport, and `paint_entities` takes the viewport's list. `.odx` stores an optional `frozen` list per viewport. The Layers panel gets a **VP** column (a snowflake per layer) while a viewport is the target (the active one, or the one picked on the sheet): click it to freeze or thaw that layer in that viewport only, one undo step (`LayerEdit::ToggleInViewport`). Not done: new viewports do not inherit a layer state.
- **Plot to PDF and SVG (done).** `PLOT` (aliases `PRINT`; also in the application menu as "Plot layout...") writes the layout being worked in to a `.pdf` or `.svg` chosen in the save dialog (PDF if no extension), from a copy of the drawing on the background worker like an export. A sheet plots at 1:1 in millimetres, as in AutoCAD practice: the drawing scale is each viewport's scale, so there is no separate plot-scale setting. Pure geometry in `od_core::plot` (`plot_layout`: sheet objects as they are, each viewport's model content mapped through its scale, clipped to its window by Liang-Barsky, minus layers frozen in it and off viewports; curves flattened to 0.02 mm; foreground and white plot black; lineweights in mm with a 0.1 mm floor), the writers in `od_files::plot` (SVG, and a hand-written one-page PDF with no dependency). Checked in two independent PDF readers (pypdf, MuPDF) and a browser for the SVG.
  Not plotted: wide polyline segments (single lines, with a note), viewport borders (draw a rectangle on the sheet), linetypes (the drawing does not draw them either), margins and plot area.
- **DXF layouts (done).** A drawing with layouts is exported as **DXF R2000** (`dxf/write2000.rs` and `write2000/{tables,entities,objects}.rs`); one without stays R12. It keeps named layouts (`LAYOUT` objects in `ACAD_LAYOUT`, tab order, sheet size in mm), a block record and block per space (`*Model_Space`, `*Paper_Space`, `*Paper_SpaceN`), what is drawn on each sheet (the first sheet's entities in `ENTITIES` with group 67 = 1, the others inside their blocks, as AutoCAD writes them), the sheet-wide viewport AutoCAD expects first, and each viewport (scale as height over view height, lock flag 0x4000, off as status 0, layers frozen in it as 331 handles). R2000 also keeps lineweights and true colours (420), and writes rectangles and polylines as `LWPOLYLINE` with bulges and widths. Reading (`dxf/read/layouts.rs`) is the reverse for R2000 and later: `LAYOUT` objects, owner by 330 / 410 / the block it sits in, sheet size from the plot settings (else the limits), viewport view centre as target plus DCS centre, frozen layers by handle, and sheet coordinates shifted by the left and bottom margins (a layout's origin is its printable area). Old files with one unnamed paper space get an implicit "Layout1". Skipped with a warning: viewports that are not plan views (rotated, twisted, perspective); non-rectangular viewport outlines come in as rectangles, with a warning.
  Checked against an independent implementation, not AutoCAD: `tests/fixtures/check_layouts.py` loads our output with ezdxf (strict read, audit with no errors, layout names, sheet sizes, viewport scales, flags and frozen layers), `check_handles`-style tests in Rust verify unique handles and that every reference resolves, and `ezdxf_layouts.dxf` (made by `make_ezdxf_layouts.py`) is read back. A file that matters should still be opened in AutoCAD.
Not done from the specification: non-rectangular viewport clips, perspective and twisted views, annotative scales, plot scale, margins and plot area, PDF/SVG plotting, DXF `LAYOUT`/`VIEWPORT` read and write (needs more than R12), text and dimensions on sheets (the app has none yet), the LAYOUT Set option, and a ribbon Layout tab.

## Dimensions (done, first slice of `private_material/dimensioning_system_specification.md`)
DIMLINEAR (`DLI`), DIMALIGNED (`DAL`), DIMRADIUS (`DRA`), DIMDIAMETER (`DDI`) and DIMARC (`DAR`) in the ribbon's Annotate tab. Built on the existing model, not the specification's slotmap/nalgebra/handle database or RealDWG: `Entity::Dimension(Box<Dimension>)` holds the defining points (`DimKind::{Linear, Radial, ArcLength}`), a copy of the `DimStyle` it was made with, the text (`DimText::{Measured, Hidden, Custom}`, `<>` stands for the measurement) and an optional user text position. `Dimension::picture()` works the lines, arcs, filled arrowheads (a tapering wide polyline) and text strokes out from those every time, so painting, picking, snapping, window selection, plotting, Explode and DXF export all see ordinary entities. All maths is pure in `od_core::dimension` with tests: measurement (aligned, rotated by projection, radius/diameter, arc length by directed sweep so arcs across 0 and major arcs work), text formatting (`DIMLFAC`, `DIMRND`, units via `format_length`, zero suppression, `DIMDSEP`, `DIMPOST`, `%%c %%d %%p`), fit (`DIMATFIT`, `DIMTIX`), placement (`DIMTAD`, `DIMJUST`, `DIMTIH`/`DIMTOH`, `DIMGAP` breaks), grips, transforms and stretch.
- **Style.** The drawing has one current style (`Document::dim_style`, set by the undoable `SetDimStyle` action, saved as an optional `dim_style` in `.odx`). The variables DIMSCALE, DIMASZ, DIMTSZ, DIMBLK, DIMEXO, DIMEXE, DIMTXT, DIMGAP, DIMCEN, DIMTAD, DIMJUST, DIMTIH, DIMTOH, DIMTIX, DIMTOFL, DIMATFIT, DIMTMOVE, DIMSD1/2, DIMSE1/2, DIMLFAC, DIMRND, DIMLUNIT, DIMDEC, DIMZIN, DIMDSEP, DIMPOST and DIMARCSYM read and set it (`dim_vars.rs`). New dimensions copy it; existing ones keep theirs.
- **Text** is multiline text: the picture holds an `MText` piece (`dimension/font.rs` measures and places it), so it uses the bundled DejaVu Sans, plots as filled glyphs (`plot_text::object_fills`) and is picked by its frame. The style is `DimStyle::text_style` (DIMTXSTY, set by name; saved in `.odx` as an optional `text_style` that must exist). Its fit and clearance sums are made in the Standard style (entities do not know the document's styles), but painting (`dash_paint.rs`) and plotting use the real one, so a width factor or slant shows. The arc-length symbol is not in the font, so `arc_length.rs` draws it as a small arc. DXF export writes a dimension's words as real `MTEXT`, and all multiline text now exports: the R2000 writer (`write2000/text.rs`) writes `MTEXT` with its style, background and long-text chunks, and a `STYLE` table of the drawing's text styles (the bundled font goes out as Arial; columns are not written; characters beyond Latin-1 as `\U+XXXX`). A drawing with text is always written as R2000.
- **Commands** (`dimension_cmd.rs`): two origins or Enter to pick an object, then the line location with Text, and for DIMLINEAR Horizontal, Vertical and Rotated (otherwise it runs across the way the cursor is). Radius and diameter: pick an arc or circle, then where the text goes (a click outside the circle keeps the text there). DIMARC: pick an arc, then the dimension arc.
- **Grips:** each defining point, then the text (dragging it fixes the position; `Dimension::reset_text` clears it). Properties shows the measurement.
- **Files:** `.odx` is now version 6; a dimension stores only the style values that differ from the stock style. DXF export writes a dimension as its picture (lines, arcs and strokes), with a note; DXF import still skips dimensions.
Not done from the specification when this slice was written, and since built: the named style table and dialog, associativity, angular, baseline, continue, ordinate, jogged, DIMEDIT, real DXF dimensions, alternate units and tolerances (see the sections below, from "Editing dimensions"). Still not built: annotative scales, DIMJUST text-follows beyond what is noted, dimension colours/linetypes/lineweights, DIMBREAK, DIMINSPECT, the DWG adapter, arrowhead blocks.

## Multiline text (in progress: slices 1 and 2 of `private_material/mtext_specification.md`)
Slice 1 is the data model, the file format and the lossless parser. There is no way to create text in the app yet and nothing draws glyphs: an `MTEXT` already in a `.odx` file loads, validates, saves back byte for byte, and is drawn, picked and snapped as its reference frame.
- **Entity.** `Entity::MText(Box<MText>)` (`od-core/src/mtext/`) with AutoCAD's fields: insertion, direction vector, nominal height, reference width (0 = no wrap), the nine attachments, flow, text style, `contents` (the exact format-code stream, the authority), entity line spacing, background mask, columns (kept and checked, not laid out) and preserved fields (group 441, unknown background bits). `MText::validate` is wired into `Document::validate`.
- **Text styles.** `TextStyleId`, `TextStyle` and `FontDescriptor` (`text_style.rs`); `Document` owns the table with `Standard` (id 0) always first, a current style and a never-reused counter (`document/text_styles.rs`). Names are unique ignoring ASCII case. No UI, action or undo for styles yet.
- **Parser.** `od_core::text::parse` tiles the contents into nodes with byte ranges (text, tab, escapes, `\P`, `\~`, `\U+XXXX` with surrogate pairs, groups to eight deep, `\H \W \T \Q \C \c \A \L \O \K`, font and stack payloads, fields), keeps anything it does not understand as an opaque node with a reason and a diagnostic, and enforces the limits (1 MiB, 100,000 nodes and paragraphs) before allocating. A fuzz-style test checks that nodes always tile the input.
- **Paragraph controls are opaque.** The specification calls for AutoCAD-made fixtures before decoding first/left/right indents, tabs, alignment, spacing and lists, and we have none. `\p...;` is kept whole as an opaque node, its paragraph is marked `protected`, and `ParagraphStyle` (Autodesk's exact alignment and numbering enums) always reads as the default. Note: the specification says `\p` is an explicit line break; the published format codes use `\p` for paragraph properties and `\P` for the break, and that is what the parser does.
- **Frame, grips, transforms.** `MText::frame` is the reference box, sized by an estimate (line count, longest line, width) until a layout engine measures it. Grips: insertion (move) and, when it wraps, the right edge (width). Snaps: insertion, four corners, four edge middles. Move, Rotate, Copy, Erase, Stretch (by insertion point) and uniform Scale work; Scale rewrites absolute `\H` heights. **Mirror is refused** (no MIRRTEXT policy) and so is Scale of text holding a paragraph control (`Entity::mirror_refusal`, `scale_refusal`; the commands say why and change nothing). Nonuniform scale does not exist in the app.
- **Files.** `.odx` version 7 (text styles, `mtext`); versions 1-6 get `Standard`. A drawing with only the stock style writes no style table. DXF export leaves text out and says so; DXF import skips `MTEXT` as before.
- **Properties** shows insertion X/Y, rotation, text height and width.
**Slice 2 (milestone 6): layout and painting.** Text now draws as real glyphs. `od_core::text::layout_text` shapes with `rustybuzz` in the bundled DejaVu Sans (licence in `od-core/assets/fonts`; it is a Bitstream Vera-style licence, not SIL OFL as the specification says), wraps, tabs, spaces lines and reports what it skipped; the canvas fills glyph outlines (`lyon_tessellation`, cached triangles per glyph and size). Frame, bounds, picking, snapping and grips come from the same layout. Checked in the real app: wrapped text, `\H \C \c \L \K \O \Q`, tabs, accents, Greek, Cyrillic, Arabic and Hebrew, rotation and the attachments. `od_core::aci` now holds the ACI colour table (moved from `od-files`).
Decisions to revisit: the default tab interval is 4 text heights and the line pitch 5/3 of the text height, both placeholders until measured against AutoCAD; a word wider than the box runs past it (the specification's rule); stacks draw as plain text, fields draw nothing; bidi is only per run (a line mixing directions is not reordered); right-to-left lines have approximate source ranges; `` fonts and non-bundled styles fall back to DejaVu with a diagnostic; DejaVu has no CJK, so ideographs show as empty boxes.
Not done: the style-aware `Document::object_bounds` (context-free queries use `Standard`), carets and cluster maps for the editor, stacked fractions, installed fonts, bold/italic faces, glyph-level hit testing, plotting text (skipped in PDF/SVG), the MTEXT command and editor, text-style commands, DXF `STYLE`/`MTEXT` read and write (AC1015), Properties rows for contents/style/attachment, paragraph and list decoding.

**Slice 3: plotting and the MTEXT command.** `PlotSheet` gained `fills` (`PlotFill`: contours filled with the non-zero rule). Text plots as filled glyph outlines in millimetres (`od-core/src/plot_text.rs`: curves flattened to the plot tolerance, same-coloured pieces joined, white plots black, viewport clipping by Sutherland-Hodgman per contour), written as SVG `<path fill-rule="nonzero">` and PDF `f`. Fills are painted after the strokes, so text always sits over lines.
MTEXT (alias `MT`; Draw > Text and Annotate > Multiline Text, replacing the unregistered `draw.text` and `annotate.text`): first corner, then the opposite corner with Height, Justify (TL..BR), Rotation and Width options (a rubber-band box), then the text typed at the command line, where `\P` starts a new paragraph and other format codes are typed as written. Enter on an empty line adds nothing; one undo step. The box-to-insertion maths is `od_core::mtext::place_in_corners`. Height (`TEXTSIZE`) and justification are remembered and saved with the user's settings (`text_memory.rs`). Fixed on the way: the command line treated a space as Enter even at a text prompt, which split typed text into commands; text prompts now keep their spaces.
Not done: the in-place editor (until then text is typed at the command line, so it cannot be edited after it is made, other than through Properties' position, rotation, height and width), `-MTEXT`, `MTEDIT`/`TEXTEDIT`, the Style, Line spacing and Columns options, the AutoCAD default of asking for the text height first.

**Slice 4: the in-place editor, plain-text baseline (milestone 2 of `private_material/mtext_wysiwyg_editor_specification.md`).** MTEXT now opens an editor in place after the box is dragged; MTEDIT (aliases `TEXTEDIT`, `ED`) opens it on a text already in the drawing (preselected, or clicked). The editor is a draft: the command passes it a copy (`Editor::edit_mtext`, `Wants::MTextEditor`, `Reply::MText`) and gets text back, so the drawing's history sees nothing until Accept, which is one undo step; Esc or Cancel leaves no trace, and an empty or unchanged text adds or changes nothing.
- **Core** (`od-core`): `TextLayout::carets` (a stop between clusters, with its byte offset in the contents, where its cluster ends and the characters either side), caret navigation (`step`, `word_step`, `word_at`, `line_start/end`, `vertical`, `nearest_caret`, wrap affinity through `caret_at(source, upstream)`), `selection_rects`, and `text::replace_text` / `escape_for_contents` / `plain_text_of`. An edit refuses to cut a control in two, to cover a control that is kept but not understood (paragraph controls), or to cover one end of a `{ }` group; typed text is escaped, so it can never be read back as a control.
- **State** (`od-app/src/mtext_editor/state.rs`, no egui): caret and selection as byte offsets, insert, backspace and delete by cluster or word (a formatting control between the caret and the cluster stays), clipboard text, the editor's own undo and redo (`history.rs`: 128 steps or 16 MiB, a burst of typing within 0.75 s is one step).
- **Input** (`input.rs`): typed text (one edit per frame, at most 4,096 characters), arrows with Shift and Ctrl, Home and End, Backspace and Delete, Enter (a paragraph break), Tab, Ctrl+A, Ctrl+Z, Ctrl+Y and Ctrl+Shift+Z, Copy, Cut and Paste, input-method preedit and commit, Ctrl+Enter to accept and Esc to cancel.
- **Window** (`window.rs`): the draft is painted in its own place, size and rotation from the same layout the drawing uses, in a box over the original, with selection, a blinking caret, pointer placing, dragging, double click for a word, triple click for a line, the input method's window position, and a small toolbar (undo, redo, OK, Cancel, why an edit was refused). A click on the drawing outside the box and toolbar accepts. While it is open the command line, dynamic input, shortcuts and canvas selection leave the keyboard and the pointer to it.
Not done from the specification: character formatting (the toolbar of the reference screenshot: style, font, height, bold, italic, underline, colour, stack), the ruler with indents and tabs, the paragraph dialog, lists, columns, fields, find and replace, spell check, double-clicking a text in the drawing to edit it, a width handle on the box, text input with Shift+Enter as a line break distinct from Enter, a visible composition run inside the text (it is drawn beside the caret), a manual check with a real input method, and the DPI and multi-monitor matrix.

**Slice 5: character formatting (milestone 3 of the editor specification, without bold, italic and fonts).** The toolbar (`mtext_editor/toolbar.rs`) now has underline (also Ctrl+U), overline, strike-through, a colour menu (ByLayer, the seven standard indexes, a custom colour picker), and height, oblique angle, tracking and width fields. Each shows what the selection looks like, or "mixed" when it differs, and a change is a `CharEdit` handed to the core.
- **Core** (`od-core/src/text/format.rs`): `format_in(contents, height, range)` gives a `SelectionFormat` of `Mixed<T>` values (a bare caret looks like the text just before it); `apply_char_edit` wraps the selected text in a `{ }` group opened with the controls (`\L \O \K \H \C \c \Q \T \W`), as AutoCAD writes it. A range that is exactly the inside of a group, or sits after that group's controls, adds its controls to it, so toggling the same text again never nests deeper. It refuses a range that splits a group or cuts a control, covers a control that is not understood, a value that is not a usable number, more than eight levels, or text over the limit. Layout and the queries share one `CharState` (`text/charstate.rs`).
- **Editor state** (`state/formatting.rs`): a format chosen at a bare caret is pending; typing then goes into one group (extended while the caret stays just after it), the group is one undo step with the typing, and moving the caret drops the pending format. Dragging a number is one undo step (`Kind::Format`).
Not done: bold, italic and font choice (the layout draws every run in the bundled regular face, so they would change nothing; they need font faces and `\f` support), stacking, the style dropdown, symbols, line spacing and justification menus, a paragraph alignment row, the ruler. A change is not yet drawn in the toolbar's colour swatch for colours it cannot name.

**Slice 6: bold and italic.** The layout now draws in four bundled faces (DejaVu Sans Regular, Bold, Oblique and Bold Oblique, `od-core/assets/fonts`). A `\f` font control (`\fFamily|b1|i0|c0|p34;`) sets bold and italic for what follows (a flag it leaves out is off), a group restores them, and a style whose font is a TrueType with bold or italic starts in that face. Each glyph carries its `FontFace`, and outlines, painting and plotting key on it. The toolbar has B and I (Ctrl+B, Ctrl+I), with mixed, selection and pending-at-the-caret behaviour like the other formats. Bold and italic are written as a font control that keeps the family, character set and pitch of the font already in effect, or the style's family (the bundled one for a bundled-font style), so only the flags change (`od_core::text::fontctl`, `apply_char_edit(.., family)`). The "font substituted" note now appears only for a family other than DejaVu Sans.
Limits: every other family still draws in DejaVu (with the note), so `\fArial|b1;` draws bold DejaVu; the toolbar's bold and italic do not read the style's own flags (a bold style shows B off, and clicking it writes `b1`); no font menu yet; DejaVu has no CJK glyphs.

**Slice 7: stacked text.** `\S1/2;` is laid out as a fraction instead of plain text. `od_core::text::split_stack` takes the payload apart at its first unescaped `/`, `^` or `#` (a backslash makes a divider literal). In the layout (`layout/items.rs`) a stack is one unbreakable cluster: numerator and denominator at 70% of the text height, centred over each other, with a bar (`DecorationKind::FractionBar`) for `/`, no bar for `^` (tolerances) and a slash between a raised and a lowered part for `#`. Being one cluster, a stack wraps, takes a caret, is selected, deleted, painted and plotted like a letter; it takes the colour, size, bold and underline round it; the frame grows to hold what hangs below the last line. Text with no divider reads as plain text. In the editor the `a/b` button (`od_core::text::toggle_stack`) stacks selected text such as `1/2` and unstacks a selected stack, one undo step each; it refuses a selection with no divider, with formatting in it, or with `;`, `{`, `}` or `\` in it, and says why. `LayoutIssue::StackNotStacked` is gone.

**Editor polish.** The wheel still zooms while the editor is open (`View::set_wheel_through_exclusions`; clicks stay excluded). The cursor prompt label ("MTEXT Edit text") is not drawn while the editor is open. Double-clicking a multiline text with no command running selects only it and runs MTEDIT (`CanvasOutput::double_click`).

**Slice 8: paragraph indents and tab stops (layout only).** `private_material/MText Example.dxf` and its PNG (made in AutoCAD, text height 1) confirm three `\p` forms: `\pxt2;` (a tab stop 2 units in), `\pxi4;` (first-line indent 4) and `\pxi-4,l4;` (hanging: first line at 0, the rest at 4). `text::paragraph::decode` reads exactly those (`i`, `l`, `t` with more stops after it as bare numbers); everything else stays opaque and protected. Layout starts each line at the paragraph's left indent (plus the first-line indent on its first line), wraps from there, and takes tabs from the paragraph's stops before the default grid. Scaling the text scales the indents and stops. Not done: the ruler and a paragraph dialog to set them, a new paragraph inheriting its predecessor's control when Enter is pressed, right indent, alignment, spacing, lists and tab kinds (no AutoCAD sample yet), and `^I` in DXF values (the DXF MTEXT reader will turn it into a tab).

**Slice 9: the ruler.** A strip above the editor's box (in the text's own direction, so it follows a rotated text) shows the caret paragraph's indents and tab stops. The top marker is the first-line indent, the bottom one the left indent (moving it keeps the first line's distance from it), and an L is a tab stop. Drag a marker to move it (ticks and snapping are a tenth of the ruler's tick step); click the ruler to add a tab stop; drag a tab 40 px off the ruler to remove it. A drag is one undo step. Core: `text::paragraph_edit` (`apply_paragraph_edit` rewrites each paragraph the selection touches, adding, rewriting or dropping its `\p`, and maps the caret through the change; `paragraph_view_in`). A paragraph with a control we do not decode shows a dimmed ruler and refuses edits. Enter now carries the paragraph's indents and tabs into the new paragraph, as AutoCAD does. Not done: the width handle at the ruler's right end, a paragraph dialog, tab kinds (centre, right, decimal) and right indent, which wait on AutoCAD samples.

**Slice 10: width handle and Paragraph dialog.** The ruler's right end has a handle (a blue bar at the wrapping edge; at the text's own width when it has none). Dragging it sets `reference_width` (one undo step per drag, never below one text height); the editor's undo snapshots now carry the width. A new `¶` toolbar button opens a Paragraph dialog with First line and Paragraph (left) indents and a tab-stop list (add, remove), the same `ParagraphEdit` the ruler uses; the paragraph being protected greys it out. Fix found on the way: a number field in the toolbar or dialog now keeps the keyboard while it is typed in (the text used to take the keys back every frame). Not done: right indent, alignment, spacing and list controls and tab kinds (no AutoCAD sample yet), clearing the width back to automatic.

**Slice 11: alignment and the carry-over rule (from `MText Example 2.dxf`).** The second AutoCAD sample shows three things. `\pxqr;`, `\pxqc;` and `\pxqj;` are right, centre and justified (`ql` for left is from published notes, not the sample). A list is not a control: it is text (`1.` and a tab, `A.`, or a Symbol-font bullet in a `{}` group) under `\pxi-3,l3,t3;`, and only the first item carries that control, so a paragraph control **holds for the paragraphs after it** until another one. That replaces the earlier "that paragraph only" rule: parsing, layout, `apply_paragraph_edit` (a changed paragraph pins the ones after it to their old look with a control only where needed) and Enter (the new paragraph just inherits; `carry_paragraph` is gone) all follow it. Layout: right and centre shift each line within the wrapping width (the widest line when there is none); justified spreads the spaces of every line that does not end its paragraph, moving glyphs, caret stops and decorations together. The toolbar has left, centre, right and justify buttons for the caret's paragraph. Not done: list buttons (bullet, numbered, lettered: they would insert the text and the hanging control; the sample's `3` indent for text height 1 does not say how it scales), distributed alignment, right indent, paragraph spacing and tab kinds (no sample), and `^I` in DXF values.

**Slice 12: lists.** `MText Example 2.dxf` has all four list kinds, and each is text under the hanging control `\pxi-3,l3,t3;` (item markers `1.`, `a.`, `A.` plus a tab, or `{Symbol|b0|i0|c2|p18;·<tab>}` for a bullet). `od_core::text::list` (`apply_list`, `list_kind_in`) writes exactly that: markers on each selected paragraph (numbered from 1), the hanging indent through `apply_paragraph_edit` (so only the first item carries the control), and "off" removes both; a different kind replaces the markers. The toolbar has a bullets and numbering menu (Off, Bulleted, Numbered, Lettered lowercase and uppercase) showing the current kind. The indent is three text heights, a guess from the sample (all height 1); check it against AutoCAD at another height. Enter in a list item (`break_list_item`) starts the next item with the next marker (the text after the caret moves to it), and Enter in an empty item ends the list, each as one undo step; items after an inserted one are not renumbered. Not done: renumbering the items after an inserted one, continuing the numbering of a list above, nested lists, and a list's own text style. Fixes found on the way: clicking a menu, dialog or toolbar popup over the drawing no longer accepts the editor (only a click on the drawing itself does), and the wheel zooms with the pointer over the text box too.

**Editor stress tests** (`mtext_editor/state/stress_tests.rs`). Seeded random sessions (typing, deleting, moving, selecting, every kind of formatting, stacks, paragraphs, lists, widths, cut, paste, undo and redo) run from empty text and from hostile contents (malformed and unknown controls, deep groups, odd Unicode). After each step they check that the contents still parse and stay within limits, every caret index and selection is inside the layout and the contents, the layout is finite and not stale, the highlight reaches the last letter, and, at the end, that undoing everything restores the start (when no step was dropped), redoing restores the end, and each redo step matches the undo that led to it. A typing model checks plain typing against a simple string. The quick versions run with the normal tests; `cargo test --release -p od-app stress_ -- --ignored --nocapture` runs 800 long sessions and a large-text run, and `STRESS_SEED=<n>` replays one. `STRESS_SHRINK_FILE` shrinks contents that break an invariant to the smallest that still do. It found one real bug at once (a paragraph control where a line wraps reported its position as the end of the line before, so a caret stop lay beyond the text). Measured in release: bold over 5,000 paragraphs 44 ms, numbering them 66 ms, a keystroke in 10,000 characters 2.4 ms, 50,000 characters 17 ms, 200,000 characters 79 ms (the whole text is laid out on every keystroke); the 1 MiB limit refuses a paste, and eight levels of nesting hold.

**Editing-session stress test** (`state/stress_model.rs`). The same idea, driven the way a user edits: through the real input layer (keys, Shift, Ctrl, Tab, Enter, Backspace, Delete, copy, cut and paste with a real clipboard, Ctrl+A, Home and End, arrows) with a plain string model beside it. After every step the text, the selection and the clipboard must match the model, and each edit must undo to the exact earlier text and selection and redo to the later ones (every edit is its own undo step in this test). Word moves, Up and Down, word deletion and mouse clicks, double-clicks, triple-clicks and drags, which the model cannot predict exactly, are checked instead for: the text does not change on a move, a word deletion removes one run that touches the caret (or exactly the selection), and the selection stays where the editor says. Both unwrapped and wrapped text run (Home and End are screen lines, so a wrapped session steps instead). 600 sessions of 600 steps pass. It confirmed that Left and Right collapse a selection to its left or right edge, as in Windows.
Not done: automatic stacking of typed text (AutoCAD's Auto-stack setting and its properties dialog), a stack's own size and alignment options, editing a stack's two halves in place (unstack, edit, stack again), stacked text on a line taller than the line pitch allows for (the following line can sit close).

## DWG import (in progress: phases 0 to 4 of `private_material/dwg_support_specification.md`)
- **Where it lives.** The reader is its own crate, `od-dwg`, with no dependencies at all (not even `od-core`), so it can be lifted out of the app. The specification put it in `od-files/src/dwg/`; the plan now is that `od-dwg` decodes a DWG into its own plain types and `od-files` gets a thin `DwgFormat` that turns those into a `Document` (specification phases 3 to 5). The app opens DWG since phase 4 (below); writing is not built.
- **Built (phases 0 and 1).** `DwgVersion::probe`, `DwgError` with a stage and offset and a `user_message`, `DwgLimits` (the specification's defaults plus `max_page_bytes`), a bounded `Cursor`, both checksums, both XOR masks, the page decompressor, and `Container::open` / `read_section`. Opening decodes the file header block (CRC checked), then the page map and section map (checksummed, decompressed). `read_section` assembles a named section from its pages, checking each page header, both checksums, the declared sizes and the cancellation flag. All three supplied drawings (AC1024, AC1027, AC1032) open, and the five sections the importer needs (`AcDb:Header`, `Classes`, `AcDbObjects`, `Handles`, `AuxHeader`) read in full. `AcDb:Header` and `AcDb:Classes` begin with the sentinels the Open Design document lists, which checks the decompressor against something other than itself.
- **Where the Open Design document and our specification disagree** (the document and the real files win): the specification says the page map and section map are XOR-masked with "AdSkanalge". They are not. Only the 0x6C-byte block at file offset 0x80 is masked (with a generated sequence), the two maps are ordinary compressed system pages with a 0x14-byte header, and the 32-byte header of each data page is masked with `0x4164536B ^ address`. Also: the printed mask table in the document is 92 bytes of 108 (the generator in the same section gives all of them); a compressed page ends with its `0x11` terminator followed by two zero bytes the document does not mention; and the byte at file offset 0x0B is not a small maintenance number in the supplied files (226, 125, 0), so `maintenance_version()` returns it raw and it should not be trusted until the header section is decoded.
- **Tests.** Unit tests per module, and `tests/containers.rs` against the three drawings in `private_material/` (size and SHA-256 checked first, with a small SHA-256 in `tests/common`): sentinels, multi-page assembly, every limit, the total budget, cancellation, unsupported and foreign files, encryption flag, a bad header CRC, a byte flipped across each file, and truncation. Not done: fuzzing, and an independent reader to cross-check section contents.
- **Built (phase 2).** `BitReader` (every code in the specification's chapter 2: B, BB, 3B, BS, BL, BLL, BD, DD, 2RD/3RD, 2BD/3BD, extrusion, thickness, OT, TU, handles), modular chars and shorts, the 16-bit CRC, `parse_object_map` (checksummed blocks, strictly increasing handles, offsets inside the section), `parse_classes`, `read_object` (size, handle-stream length, CRC, the data/string/handle split), the common object and entity fields, and `Inventory::read`, which ties them together. All three drawings inventory with no dangling reference, every object's own handle matching the map's, and the same content in each generation (3 each of LINE, CIRCLE, ARC, TEXT and MTEXT, 2 VIEWPORTs, 2 LAYERs, 2 LAYOUTs, 17 classes). Object counts are 218, 169 and 155; the rest is dictionaries, XRECORDs and the like that differ by release.
- **More places the Open Design document and the real files differ** (the files win): the printed table of object type codes is shifted for the table entries, so LTYPE_CONTROL is 0x38, LTYPE 0x39, VIEW_CONTROL 0x3C, VIEW 0x3D, UCS_CONTROL 0x3E, UCS 0x3F, VPORT_CONTROL 0x40, VPORT 0x41 (checked on the control objects, whose handles 5 to 9 are fixed by AutoCAD). The "no links" bit listed in the common entity data is not there in R2010 and later. The object size counts only the body, not the size and handle-length fields before it, and the object CRC (start value 0xC0C1) covers those fields too. The class region begins with a 32-bit count of its used bits, which says how many padding bits end it. The handle map's CRC also starts at 0xC0C1 and covers the block's size field.
- **Not checked against AutoCAD.** The expected counts in `tests/inventory.rs` were read off our output and cross-checked (a separate script for framing and type codes, handle and CRC agreement, the three generations agreeing), not compared with a listing from AutoCAD. A listing of the drawing's objects (`LIST` on the lines, circles, arcs, text and mtext; layer and layout names) would close that. True-colour entities (the `BL` RGB after a colour with the 0x8000 flag) and entities with extended data or a proxy graphic are decoded as the specification says, but no supplied drawing has any.
- **Built (phase 3).** In `od-dwg`: `AcDb:Header` (every variable is read so the data and string streams must end exactly on the last field; units, current layer, model and paper space blocks and `HANDSEED` are kept), the LAYER, LTYPE and BLOCK_HEADER records, LINE, CIRCLE, ARC, LWPOLYLINE and the old 2D POLYLINE with its VERTEX records, the OCS to WCS rule for extrusions (+Z, and -Z as a mirror in X; anything tilted is skipped), validation of every number, and `Drawing::read`, which resolves handles in a second pass and returns the layers, the model-space shapes in drawing order and a typed `ImportReport` (exact, normalised, degraded and skipped counts by kind). "By block" on a top-level entity becomes "by layer" with a note. In `od-files`: `DwgFormat` converts a `Drawing` to a `Document` (units, layers with new ids, attributes), runs `Document::validate`, and words the report in stable sentences (`dwg/warnings.rs`). `FileError::Unsupported` separates an old version, a protected file or a size limit from damage. **`DwgFormat` is not in `FORMATS` and the app does not know it exists; that is phase 4.** The three drawings import to 9 entities (a line, a circle and an arc, three times over: layer 0, "Test Layer", and "Test Layer" with colour 3 forced), skipping 3 TEXT, 3 MTEXT and 2 paper-space viewports, and every generation gives the same document.
- **More places the Open Design document and the real files differ** (the files win): in a LAYER and in a BLOCK_HEADER there is no "64 bit" flag and no "xref dependent" bit, only the xref index short then the flags; in a layer the flags short is frozen 1, **off** 2, locked 8, plot 16, lineweight (mask 0x3E0, 31 meaning default); the CMC colour's index is 0 and the real colour is in the packed long (0xC3 in the top byte then the index, 0xC2 then RGB); a block record's handles start with a null pointer before the BLOCK entity, then its entities in drawing order, ENDBLK and the layout; an entity's lineweight byte is 29 for ByLayer, 30 for ByBlock and 31 for default; the length of a BLL is a plain 3-bit number (not a 3B code), as the R2013 and R2018 headers show; the header has one more (empty) text than the list gives, no trailing four shorts, and random fill after its last handle; strings are not NUL-terminated.
- **Real-world files that once failed (checked on a 16-drawing set of R2018 site drawings, all now open).** Three more places the files win: the bytes after the end sentinel of the header and class sections are padding of any length and may hold stale data (up to 18 bytes seen, once with the tail of an old sentinel), so they are not checked; the same goes for bytes after the empty block that ends the handle map (522 stale bytes seen); and an xref's BLOCK_HEADER (or an overlaid one) stores no owned object count, so reading one shifted every later field and ended the whole import with "ended too early". Before these, the message "not a readable drawing (header is damaged)" appeared for a drawing that was fine.
- **Not checked against real files.** None of the supplied drawings has a polyline, a rotated or mirrored entity, an entity with a Z, a true colour on an entity, or extended data, so LWPOLYLINE, 2D POLYLINE and VERTEX decoding, the extrusion handling, elevation flattening and widths are tested only with data written by `testkit::BitWriter` from the same specification (which proves the reader and the writer agree, not that either is right). A drawing with those (a rectangle, a polyline with arcs and widths, a mirrored arc, a block with a Z) is the next fixture to get.
- **Built (phase 4): the app opens DWG.** `DwgFormat` is in `FORMATS` (after native and DXF), so the Open dialog lists "AutoCAD DWG" and "All drawings" takes `*.dwg`, and the dialog, recent files, drag and drop and a path on the command line all reach it through `format_for`. `FileFormat` gained two optional methods: `read_cancellable` (the default calls `read`; DWG passes the flag into the reader) and `check_size` (DWG refuses a file over `DwgLimits::max_file_bytes` from its length, before `fs::read`). `od_files::load_cancellable` checks the size, reads and dispatches; `load` calls it with a flag that is never set, and the app's open job now passes its Cancel flag. An import is unsaved with no path, says "Imported <file>: N objects (see the command line for what was left out)", and Save offers `.odx` only (`native_path("plan.dwg")` is `plan.odx`; saving to a `.dwg` name is refused). Tests: open filters, the size limit, load and a cancelled load in `od-files`; in the app, a dropped DWG imports and saves natively, a damaged one installs nothing and leaves recent files, and a cancelled import installs nothing and can be tried again. Checked in the real app with `Test Drawing 2018.dwg` given on the command line (9 objects, two layers, the TEXT/MTEXT and paper-space warnings in the command line).
- **Larger drawings (fixed 14-10-2026).** "Pipe Fittings.dwg" (an R2018 drawing of 30,589 objects) was refused as having "an invalid entry in its object map". The handle map is split into blocks of about 2032 bytes, and each block starts its handle and offset totals from zero (its first pair is absolute); we had carried them on from the previous block, which only drawings small enough for one block (all of the supplied ones) never showed. AutoCAD also lets a block run a few bytes past 2032 (it stops adding pairs once past), so the limit is now 2032 + 16. Handles must still increase across the whole map.
- **ELLIPSE (done 14-10-2026).** Decoded from §20.4.39 (centre and major axis in world coordinates, extrusion as three plain doubles, ratio, start and end parameters); a downward extrusion runs the parameters the other way, a tilted one or an axis out of the plane is skipped as non-planar, elevation is flattened with a note. Checked on "Pipe Fittings.dwg" (not in the repository; it is the user's): all 259 ellipses come in, and every one of the 154 elliptical arcs meets the end of another object in its block at both of its ends, which the right parameters and sense give and the wrong ones would not.
- **SPLINE (done 14-10-2026).** Decoded from §20.4.40 (`od-dwg/src/spline.rs`). A DWG spline is stored either by its control frame (scenario 1: degree, closed/periodic flags, knot and control tolerances, knots, control points and, when weighted, a BD weight after each point) or by its fit points alone (scenario 2: fit tolerance, two end tangents, fit points; no control points in the file). From R2013 two BLs come first, flags (1: made by fit points, 4: closed) and the knot spacing (0 chord, 1 square root, 2 uniform, 15 custom); the flags' 1 makes it scenario 2 and custom knots make it scenario 1. Points are world coordinates with no extrusion: points at one height are flattened with a note, different heights or a tangent out of the plane are skipped as non-planar. Counts are checked against `max_collection_items` and the bits left before anything is read. `od-files` builds an `od_core::Spline` from a control frame and validates it ("Skipped N splines whose values make no spline." otherwise); a fit-points-only cubic with no end tangents is rebuilt with `Spline::from_fit_points`, or `from_closed_fit_points` when closed (chord, square root or uniform by the knot-spacing field), and keeps its fit tolerance; one with end tangents or of another degree is skipped by name. The DXF reader does the same for a SPLINE with fit points and no control points (chord knots, parameterization left unset as for any DXF spline), so ezdxf's `add_spline` now comes in. Checked against "SplineTest.dxf", where AutoCAD's own control points for a 7-point fit match the solver's to 1e-14. Knots are left at AutoCAD's scale (the chord length, the sum of the square roots of the chords, or one per span), so they match its knot vector exactly and a DXF round trip keeps them. "Spline Test 2" (DXF and DWG 2018, five splines: closed square-root and uniform fits, two open uniform fits and a CV spline) confirmed all of it: a closed fit is clamped with `n + 3` control points (first and last at the first point) and equal first and second derivatives at the join (`spline/fit_closed.rs`, banded by taking the unknowns alternately from both ends), and the DWG fits match the DXF's stored control points and knots to 1e-14 (`od-files/tests/spline_fixtures.rs`). The closing point AutoCAD repeats at the end of a closed fit's points is dropped. Closed fits are not refittable by fit-point grips yet. Checked on "Pipe Fittings.dwg": all 582 splines are control frames (cubic, open, not rational, full knot form) and all come in valid; 1,148 of their 1,164 ends meet another object exactly, at its end or along it, and the other 16 are identical pairs about 0.14 from the nearest outline (the same fittings in model space and in a block), which wrong field types would not give. No supplied drawing has a rational, closed, periodic or fit-points-only spline, so those layouts are tested only with `testkit::BitWriter` data.
- **Next (phase 5):** text and layouts (text styles, TEXT and MTEXT, layouts with paper-space ownership and plan viewports, per-viewport frozen layers).

## Blocks (in progress: increment 1, with parts of 2 and 3, of `private_material/blocks_dynamic_blocks_specification.md`)
- **Built: the static block foundation.** A block table on the `Document` (`BlockDef`: id never reused, name unique ignoring case and checked against AutoCAD's rules, base point, description, objects with their layers and properties) and a new entity kind, `Entity::Insert` (block, insertion point, X and Y scale, rotation). An insert holds its definition as a shared `Arc`, the same record the table holds, so every insert of a block shares one copy and the context-free queries reach the contents without the drawing. Nesting works and cannot loop in memory. Code: `od-core/src/block/` (`affine`, `picture`, `edit`, `table`, tests) and `document/blocks.rs`.
- **How the rest of the app sees an insert:** through its picture (`Insert::picture`), like a dimension: painting, picking, window/crossing/fence selection, object snaps (the insertion point plus the snaps of every piece), plotting and DXF export. Layer-0 objects inside a block take the insert's layer (`block::inherited`); the canvas and plot draw each piece in its own colour (`Document::insert_pieces`). Move, Copy, Rotate, Mirror (kept as a negative X scale, as AutoCAD does), Scale and Stretch (by the insertion point) combine with the insert's transform; the block never changes. One grip, at the insertion point. Properties shows position, rotation and X/Y scale.
- **Commands.** `BLOCK` (`B`, `-B`; ribbon Insert > Block > Create), worded as `-BLOCK`: name (`?` lists), base point, objects (the selection, if any). The objects become one reference, as the dialog's default "Convert to block" does. An existing name asks "Redefine it?"; redefinition rebuilds every definition and insert that holds the block, in one action (`Document::redefined_blocks`), and refuses a block that would hold itself. `INSERT` (`I`, `-I`): name (default: the newest block; up to 20 block names, alphabetical, are offered as options in the command line and the dynamic-input menu, `?` lists them all), insertion point with a live preview, then the block is placed at scale 1 and rotation 0, as AutoCAD 2020's INSERT does; Scale and Rotate options at the point prompt change them first. Separate X and Y scales are set in Properties. `PURGE` (`PU`): deletes every block nothing inserts, including blocks used only inside other unused blocks. `EXPLODE` breaks a reference one level down; the parts keep their own layers and properties. Each command is one undo step (`SetBlocks` replaces the table; inserts that follow a redefinition change in the same transaction).
- **Files.** `.odx` version 8: a `blocks` list (objects in block coordinates, inserts naming their block by id) and an `insert` entity kind. Reading resolves definitions in any order and refuses a block that inserts itself, a missing block, a zero scale or a bad name. DXF export writes each reference as the objects it draws, with a note.
- **DWG text import (done 21-10-2026).** `od-dwg/src/text.rs` decodes TEXT (R2000+ layout: a flag byte marks the values left at their defaults, then insertion, alignment point, extrusion, thickness, slant, rotation, height, width factor, the string from the strings stream, generation, the two alignment codes, and the style handle), MTEXT (insertion, extrusion, X axis, box width, height, attachment, flow, text, style handle, line spacing, then the R2004 background flags with scale and colour; in a 2018 file the tail is read for the column type) and STYLE (name, xref index, vertical and shape-file bits, fixed height, width factor, slant, generation, font and big font names). `od-files/src/dwg/text.rs` makes the styles (Standard keeps the document's own id; a repeated name or a style that is not valid falls back to Standard) and turns each text into an `MText`; the same code serves blocks. A text that does not read is counted as "TEXT (unreadable)" instead of failing the file. Checked on `Pipe Fittings.dwg` (53 TEXT and 307 MTEXT, now all drawn) and the three generations of "Test Drawing" and "Test Drawing 2", which agree with the DXF. **Found in the files:** AutoCAD gives every MTEXT with a width a "dynamic" column block of count 1, so only a count above 1 means columns. **Attributes (same day):** an INSERT now lists the handles of the ATTRIBs it owns (the objects are not in the block's list), and each single-line ATTRIB that is not invisible follows its reference as text, in the model or in the block being read. Layout read from the DWG specification (§20.4.4, 20.4.5): the TEXT fields, a version byte, from 2018 the kind (1 single line), then tag, field length, flags (1 invisible, 2 constant) and the position lock. Multiline attributes carry an embedded MTEXT and are skipped by name. `private_material/blocks_dynamic_blocks_specification.md` §1.4 and §4 describe the full model (attribute definitions and references as entities, editing, `ATTSYNC`, extraction); that is not built, so an imported attribute is plain text with no tag. **Found by opening 30 real drawings:** a mask in the window colour (background flag 2) stores no scale or colour, and reading them truncated the object, which left out hundreds of MTEXT in drawings that use it (now fixed, with a test); the unreadable-text count in the import warnings is how this showed. **Not done:** multiline attributes, the attribute model above, text in a tilted or mirrored plane, per-text backward and upside-down flags (the style's are kept), "fit" stretching (read as ordinary text along the line, and reported), the width and height "annotative" data, fields, and MTEXT columns. `%%` codes are turned into characters at import in both TEXT and MTEXT.
- **Block import from DXF and DWG (done).** Named blocks and their references come in from both (`od-files/src/block_import.rs` builds the definitions for both readers; `dxf/read/blocks.rs`; INSERT and the block record's base point and description in `od-dwg`). Checked on "Test Drawing 2" (`private_material/`, DXF and the 2010, 2013 and 2018 DWGs, made in AutoCAD): `test_block` (a circle and two crossing lines, base at the origin) inserted at (30, 25) comes in identically from all four, with the dimension, text and mtext reported as skipped (`od-dwg/tests/blocks.rs`, `od-files/tests/block_fixtures.rs`). The ezdxf sample now brings its DOOR block and ezdxf's three arrowhead blocks. DXF still ignores extrusions (a -Z INSERT comes in unmirrored, as other DXF entities do); DWG mirrors it. None of the supplied drawings has a nested, rotated, scaled or mirrored reference, so those paths are tested only with made-up data.
- **Uneven scale.** Circles, arcs and ellipses under unequal X and Y scales become exact ellipses (`Ellipse::mapped`), so they are drawn, picked, snapped and exploded as ellipses; polyline arc segments become straight pieces close to the curve; text keeps its shape at the average size; wide polyline segments lose their width.

- **Block Editor (built).** `BEDIT` (`BE`; ribbon Insert > Block > Edit; double-click a reference) opens the selected reference's block, or asks for a name with the blocks offered as options. ## Ellipse (done: `private_material/ellipse_element_specification.md`, apart from the parking lot below)
- **The entity.** `Entity::Ellipse(Ellipse)` (`od-core/src/ellipse/`) is AutoCAD's `ELLIPSE`: centre, major-axis vector, minor-to-major ratio (1e-6 to 1) and a counter-clockwise parameter interval (0 to 2π for a full ellipse). `Ellipse::new` checks and canonicalises (start in [0, 2π), a whole turn becomes 0 to 2π, an end below the start goes round once); `validate` is what `Document::validate` and block validation call. Nothing derived is stored. Exact and pure: bounds (closed form for a full ellipse), angle/parameter conversion, nearest point (sampled slope, then bisection, with the ends of the axes always samples so a flat ellipse's two long sides are never mixed up; checked against a dense search on 5,000 random cases down to ratio 1e-6), flattening (even parameter steps sized from the bound a·h²/8 on chord error, so it is guaranteed rather than probed, at most 8,192 points or `ResourceLimit`), length (adaptive Simpson), translate/rotate/scale/mirror, any affine map (`mapped`, used by block pictures), splitting and grips.
- **Everywhere else.** Painting (half-pixel tolerance; a coarse fallback only if the cap is hit), hit-testing, window/crossing/fence selection, snaps (centre and the quadrants it reaches; an arc's ends and parametric middle; Nearest), grips (centre moves; axis ends resize and may swap the axes; an arc's ends move along it), Move/Copy/Rotate/Mirror/Scale, Stretch (moves it whole when the centre is caught), Break (a full ellipse needs two points, as a circle), Erase, Properties (centre, radii, rotation, ratio read-only, and for an arc start/end angle and start/end parameter labelled apart, plus length and the area cut off by its chord; circumference and area for a full one; `properties/ellipse.rs`), plotting (fails with a message rather than plot coarser than 0.02 mm), blocks.
- **ELLIPSE command** (`EL`; ribbon Home > Draw > Ellipse, Lucide's egg icon as there is no ellipse glyph; `od-app/src/ellipse_cmd.rs`): axis endpoint `[Arc/Center]`, other endpoint (or centre then axis endpoint), distance to other axis (typed, or a point measured across the first axis) `[Rotation]` (the first axis as the diameter of a circle tilted 0 to 89.4 degrees: minor = major × cos), then for Arc the start angle `[Parameter]` and end angle `[Parameter/Included angle]`. Either axis given first may be the major one. Angles and parameters are measured from the first axis endpoint given, as we understand AutoCAD to do (**not yet checked in AutoCAD**). One undo step; Esc adds nothing; bad values are refused and asked again.
- **Trim and Extend (done 14-10-2026).** An ellipse is a cutting edge and a boundary, and can itself be trimmed (a full one needs two crossings, as a circle) or, as an arc, extended round its ellipse. Crossings are exact for lines (in the ellipse's unit-circle frame) and found with bounded work for circles, arcs and other ellipses (`ellipse/cross.rs`: the other curve's level along the ellipse is a degree-two trigonometric polynomial; sample, split at turning points, bisect; a touch is judged by distance, not by the level, which a thin ellipse inflates). Checked against a 200,000-sample count on 2,919 random pairs down to ratio 1e-4: 4,436 crossings, none missed or extra.
- **Fillet (done 14-10-2026).** A line, circle, arc or another ellipse can be filleted to an ellipse, either way round, as in AutoCAD (`od-core/src/fillet_ellipse.rs`). A circle of radius r touches the ellipse at parameter t when its centre is p(t) ± r·n(t); the zeros of its miss from the other object along t (sampled, then bisected) are the candidates, and only centres truly r from the whole ellipse count (inside a tight bend the normal offset alone would cut through it). The one with touching points nearest the picks wins, as for the other fillets; an elliptical arc is cut back or extended round its ellipse, a full ellipse is not trimmed (as a circle). Radius 0 meets at the crossing. CIRCLE TTR takes ellipses the same way. Tested on fixed cases and 200 random pairs.
- **Join (done).** Elliptical arcs of one ellipse that meet end to end become one arc, or the whole ellipse when they close the turn (`ellipse/join.rs`); other objects in the selection join among themselves as before.
- **Snaps (done).** Quadrant (OSMODE 16) and Nearest (512) are new snap modes for every curve: quadrants of circles, arcs, polyline arc segments and the axis ends of ellipses; Nearest only when no other object snap is in the aperture, as in AutoCAD. Both start off, as in AutoCAD's default OSMODE; toggles QUA and NEA in the status bar, commands `view.snap_quadrant` and `view.snap_nearest`, and the Settings dialog.
- **Refused, as in AutoCAD:** Chamfer ("A chamfer needs lines or polyline segments."). Explode leaves an ellipse alone (it is already simple).
- **Files.** `.odx` version 9 adds the `ellipse` entity (all five values required). DXF reads `ELLIPSE` in ENTITIES and BLOCKS (any group order; +Z and -Z extrusions; tilted ones skipped; repeated or missing values count as damaged; `dxf/read/ellipse.rs`), and a drawing with an ellipse is written as R2000 with real `ELLIPSE` entities (R12 has none, and is refused rather than approximated). Checked with the `dxf` crate and by exporting "Pipe Fittings.dwg": ezdxf's audit is clean and all 259 ellipses read back. DWG import: see "DWG import".
- **Performance** (`cargo run --release -p od-canvas --example bench`, this machine): 10,000 visible ellipses about 8.5 ms a frame (2.6 ms building, 5.6 ms tessellating), 50,000 about 44 ms.
- **Parking lot** (decided 14-10-2026; not started):
  - *Offset of an ellipse.* The offset of an ellipse is not an ellipse; AutoCAD makes a spline. The spline entity now exists (see "Spline"), but fitting the offset curve is spline Offset work (milestone 6 of the spline specification), so OFFSET still refuses ellipses ("OFFSET does not support ellipses yet.").
  - *`PELLIPSE`* (ellipses drawn as polylines; a drawing variable) and *Isocircle* (needs isometric drafting, which does not exist).
  - *JOIN across gaps and its Close option.* AutoCAD joins arcs (circular and elliptical) of one circle or ellipse even with gaps between them, and Close turns a single arc into the whole circle or ellipse; our JOIN joins only pieces that meet, for circular arcs as for elliptical ones.
  - *Intersection snap*, and checking the ELLIPSE prompts and the R2000 DXF export in AutoCAD itself.

## Spline (baseline done 14-10-2026: milestones 1 to 3 of `private_material/spline_element_specification.md`)
- **The entity.** `Entity::Spline(Box<Spline>)` (`od-core/src/spline/`) is AutoCAD's `SPLINE`, a planar NURBS: degree (1 to 25), control points, the full knot vector (`control points + degree + 1`), optional positive weights (`None` when all are 1), closed and periodic flags, knot and control-point tolerances, and optional fit data (fit points, fit tolerance, end tangents, knot spacing). The control frame is the authority; fit data is kept as AutoCAD keeps it and never refitted on load, draw or save. `Spline::validate` checks counts, finite values within 1e12, non-decreasing knots and their multiplicity (within the knot tolerance), a domain with length, weight count and range, periodic implies closed, a closed spline's ends meeting, and fit data; `Document::validate`, block validation and both file writers call it.
- **Maths (pure, bounded, tested).** Evaluation by homogeneous De Boor about the first control point (`eval.rs`); each span as a rational Bezier piece by blossoming, so it looks only at that span's control points. Flattening (`flatten.rs`) halves a piece until its control points are within the tolerance of its chord (certain, since a positive-weight piece lies in their hull), and a run of spans whose control points fit in a box the tolerance wide is drawn as one chord without being cut at all; at most 8,192 points for the screen and 65,536 for plots, else `ResourceLimit`. Length by adaptive Gauss-Kronrod 7-15 per span; the Midpoint snap is half the length; nearest point from the outline's best stretches (at most 8) then golden-section search (checked against a 100,000-sample search). Fit (`fit.rs`): AutoCAD's cubic through the points with knots at their chord, square-root-chord or even parameters and natural ends, solved as a banded system with partial pivoting; two points give a straight cubic with control points at thirds. Transforms map control points, fit points and tangents exactly, any affine map included (uneven block scales stay exact splines).
- **Everywhere else.** Painting (half-pixel tolerance), hit-testing and window/crossing/fence selection by the curve (not its control frame), Endpoint (open splines) and Midpoint snaps, Nearest, grips (the fit points of a spline that can be refitted, otherwise the control points; moving a fit point refits, moving a control point drops the fit data), Stretch (the same points), Move/Copy/Rotate/Mirror/Scale, Erase, Properties (degree, closed, periodic, rational, counts, fit tolerance, ends and length, all read-only; `properties/spline.rs`), plotting (fails rather than plot coarser than 0.02 mm), blocks and layouts.
- **SPLINE command** (`SPL`; ribbon Home > Draw > Spline, reusing Lucide's spline glyph, which Polyline also uses; `od-app/src/spline_cmd.rs`): `Specify first point or [Method/Knots/Object]` (CV: `[Method/Degree/Object]`), then `Enter next point or [start Tangency/toLerance]`, then `[end Tangency/toLerance/Undo/Close]`; Enter ends, Esc discards, one undo step. Fit makes a cubic through the points; CV a clamped spline of the chosen degree (1 to 10; lowered with a message when there are too few points). `SPLMETHOD`, `SPLKNOTS` and `SPLDEGREE` (1 to 5) are user settings (`spline_memory.rs`), not drawing data. Not built, and said so when chosen: Object, start and end tangency, a fit tolerance other than 0, Close. Prompts follow AutoCAD 2020 as we understand them (**not yet checked in AutoCAD**).
- **Refused by name until their geometry exists:** Trim and Extend (as object, cutting edge or boundary), Break, Offset, Join, Fillet; Chamfer needs lines, as in AutoCAD; Explode leaves a spline alone.
- **Files.** `.odx` version 10 adds the `spline` entity (`native/spline.rs`; weights and fit data left out when absent; at most 100,000 points per spline read). `serde_json` now parses floats exactly (`float_roundtrip`): the default parser could come back one unit in the last place off, which the spline round-trip tests caught. DXF reads `SPLINE` in ENTITIES and BLOCKS (`dxf/read/spline.rs`): any group order, declared counts must match, sizes and a 2,000,000-number file budget checked before gathering, weights must go with the rational flag, +Z or -Z normals (points are world coordinates), tilted or uneven ones skipped as non-planar, AutoCAD's short periodic knot form and fit-points-only records (as ezdxf's `add_spline` writes) skipped by name, damaged ones counted. A drawing with a spline is written as R2000 with every knot, weight, control point and fit point; R12 refuses it. DXF files over 1 GiB are refused before reading. Checked: the `dxf` crate parses the export, ezdxf audits it clean (`examples/export_splines.rs`), and splines made by ezdxf (open, rational, fitted, closed, in a block) read back on ezdxf's own evaluated points to 1e-9 (`tests/fixtures/make_ezdxf_splines.py`). DWG import reads splines stored by their control frame (see "DWG import").
- **Performance** (`cargo run --release -p od-canvas --example bench`, this machine): 10,000 visible 8-CV cubic splines about 13 ms building plus 6 ms tessellating a frame; 1,000 splines of 1,000 control points about 11 ms plus 2 ms. Selecting 100 of the 1,000-CV splines shows 100,000 control-point grips (as AutoCAD would), about 75 ms a frame.
- **Still to do** (the specification's later milestones): exact Trim/Extend/Break/Join (knot insertion, curve crossings), Offset (and with it ellipse offset), Fillet, closed and periodic creation, end tangents, positive fit tolerance, Object conversion, SPLINEDIT and multifunction grips, Intersection/Tangent/Perpendicular/Geometric Center snaps, fitting fit-point splines with end tangents (DXF and DWG; still no AutoCAD file to check against), refitting closed fits from grips, AutoCAD-made DXF fixtures (the periodic short form in particular), and checking the prompts and export in AutoCAD itself.

## Spatial index (done 16-10-2026: `private_material/spatial_index_specification.md`)
An R-tree per space inside `Document` (`rstar`; `od-core/src/spatial_index.rs`, `document/spatial*.rs`), used by painting, hover and click picking, snapping and window, crossing and fence selection (including WPOLYGON, CPOLYGON, FENCE and STRETCH). Design and rules: `ARCHITECTURE.md`, "Spatial index". Choices that differ from or settle the specification:
- **Step 0 (decide from data):** the specification said it paid beyond about 50,000 objects. Measured (release, dev machine): a scan of 100,000 objects takes 280 us and of 1,000,000 4.1 ms, a tree query 0.3 us sparse and 22 us for 1% of the drawing (1,042 found), so it proceeds; below 4,096 objects in a space (`Config` in `document/spatial.rs`) nothing is built and queries scan as before. `Pipe Fittings.dwg` (8,741 top-level objects) therefore gets a tree in model space but is not the reason for it.
- **Frame, zoomed in:** run time 4.3 ms to 0.05 ms at 100,000 objects (10,000: 0.39 to 0.01; 50,000: 3.1 to 0.02). Full views, far-out views and the snapping scenarios of `od-canvas`'s bench are within noise of before (all objects in view take the scan path when the rectangle covers the tree); one run of "100,000, 10% selected" read 16.2 ms before and 17.6 after (p95 16.4 and 27.0) while every other scenario read equal or faster, so it is taken as noise but is worth re-measuring.
- **Build and edit costs** (`bench_index`, 100,000 / 1,000,000 uniform circles): loading with the tree built once at the end 38 / 434 ms (the tree itself 27 / 283 ms; updating the tree per object instead 104 / 1,667 ms); one replaced object 3 / 5 us; `replace_many` of 1% 2.8 / 40 ms, of 10% 28 / 324 ms, of 50% 40 / 500 ms (these rebuild once); a clone of the indexed drawing 8 / 80 ms. 100,000 objects with one and the same box build in 24 ms. Retained memory was not measured: per object the tree holds a 40-byte entry plus a map entry, so expect on the order of 100 bytes.
- **Not done:** `Document::bounds` and `model_bounds` stay filtered scans (specification section 7); no caller-owned scratch buffers (a query allocates a `Vec`, small when zoomed in); the whole-view heuristic (planner item 5) is not needed (a rectangle covering the root scans); no 1,000,000-object canvas frame measurement and no allocation counts; grips and commands that look at the whole drawing are unchanged (not audited one by one); the invariant check runs in tests only, not as a debug assertion after every edit.
- **Found on the way:** `replace_many` first checked each id against every earlier one (quadratic: replacing 1,000,000 objects took 27 s); it now uses a set and a guard test (50,000 objects, 10 s) covers it.

## Ortho (done 16-10-2026)

## Performance

Two benchmarks, both release-only: `cargo run --release -p od-canvas --example bench` (entities, ellipses, splines) and `cargo run --release -p od-app --example bench_features` (dashed linetypes, dimensions, block inserts, hatches, editing every object, and real files if present). Findings on the dev machine, 14-10-2026 onwards:
- **Fixed: bulk edits were quadratic.** `Document::remove`/`insert` each rebuilt the id lookup (a pass over every object), and three things looped over them: Erase (`RemoveEntities`), the undo of adding copies (`AddCopies`), and the DXF export of block references, dimensions and text. Erase All took 0.5 s at 10,000 objects, 30 s at 50,000 and 139 s at 100,000, undo the same; saving a DXF with 8,000 inserts took 166 s (2,000 dimensions 4.4 s; the real `Pipe Fittings.dwg` 1.3 s). Now `Document::remove_many`, `insert_many` and `replace_each` (`document/object_list.rs`) make one pass from the first object touched and update the lookup only from there. Results (100,000 objects): erase 17 ms, undo 6 ms; saving 8,000 inserts 113 ms, 2,000 dimensions 94 ms, `Pipe Fittings.dwg` 39 ms. One object removed and put back at 100,000 objects: 0 ms at the end, 1.8 ms in the middle, 4.1 ms at the front (was 5.6 to 6.5 ms everywhere). `remove` and `insert` are now thin calls into the same code; unit tests check every subset of seven objects and positions past the end against a plain list, and guard tests (50,000 objects, a 10 s limit that an unoptimised build still meets) fail if a loop comes back (architecture rule 8). A `Transaction` only groups actions into one undo step; it never batched document edits, so the fix is in `Document`.
- **Fixed: dimensions and inserts were slow to cull and hit-test.** `Dimension::bounds` built the whole picture (13 small pieces, each with its own vectors: 3.3 us of allocation against 0.1 us to take their bounds), 3.8 us per dimension against 0.03 us for a plain object (inserts 1.0 us), and culling, picking and snapping asked every object every frame or mouse move. `Object::bounds()` (`document/object.rs`) now works the box out once and remembers it; `Document::replace`, the only way an object's entity changes, forgets it, and two objects equal but for having asked are still equal. Culling, `pick`, snapping's pre-filter and `Document::bounds` use it. One hover over 2,000 dimensions: 7.4 ms to 0.01 ms; a zoomed-in frame with 2,000 dimensions: 15.6 ms to 0.5 ms (inserts 4.2 ms to 0.2 ms). A guard test (3,000 dimensions, 200 picks, 10 s limit) fails without the cache. Still open: the picture of a dimension or insert is rebuilt every frame it is on screen (2,000 dimensions all in view: 14 ms run + 11 ms tessellation); cache it per object if that matters.
- **Fixed: very fine dash patterns.** The cost of 10,000 dashed objects all in view falls smoothly with the size of one repeat (about 41 ms at 4 px, 33 at 5, 30 at 6, 26 at 7, 24 at 8, 19 at 12, 14 at 24, against 8 ms solid; `bench_features`), so there is no cliff to aim at. `MIN_REPEAT_PX` in `dash_paint.rs` is now 6 px, up from 3: a 6 px repeat is a 4 px dash and a 2 px gap, which already reads as a texture, and the worst case that is drawn went from 41 ms to about 26 ms (a 7 px repeat in the benchmark; its nominal 6 px lands just under the limit and is solid). A pattern under that is drawn solid at that zoom only (the file and plots are unaffected); 10,000 dashed objects all in view still cost about 26 ms a frame just above the limit, 8 ms solid.
- **Fixed: every frame, hover and snap walked every object.** See "Spatial index" below. Zoomed in on 100,000 objects a frame's run time fell from 4.3 ms to 0.05 ms.
- **Fine:** 10,000 plain objects 8 ms a frame, 50,000 45 ms, 100,000 85 ms when all are in view (drawing them is the cost); `Pipe Fittings.dwg` reads in 45 ms and draws in about 5 ms; dashing itself costs about 0.4 us an object.
- **Done for dimensions (16-10-2026):** `private_material/picture_cache_specification.md`, see "Picture cache". Block references are left for later on the evidence there.
- **Done:** `private_material/spatial_index_specification.md`, see "Spatial index".
- The hatch scenario in `bench_features` is not conclusive (the copied test hatches draw few triangles).

## Legacy leaders (LEADER, baseline done 18-10-2026)
`Entity::Leader` (`od-core/leader.rs`): vertices (arrowhead first; a hookline is the last horizontal segment among them, flagged), the arrow flag and size (the dimension style's `DIMASZ` times `DIMSCALE` at creation), the style's name, and a reference to the MTEXT it annotates (`annotation: Option<EntityId>`) with the height and width the file recorded. Format and the annotation options are not built.

## Donut (done 23-10-2026)
`DONUT` (`DO`; ribbon Draw flyout): inside diameter, outside diameter (each offers the last one used, 0.5 and 1 at first; either order is accepted, a bad pair is asked again), then centres with a ghost until Enter or Esc, one undo step each. ## Divide and Measure (done 23-10-2026)
`DIVIDE` (`DIV`) and `MEASURE` (`ME`), in the Draw flyout. ## Construction line and Ray (done 23-10-2026)
`Entity::Xline` and `Entity::Ray` (base point and unit direction; see ARCHITECTURE.md). **XLINE** (`XL`; ribbon Draw flyout): a point, then through points until Enter; or Hor, Ver, Ang (degrees; Reference is not built), Bisect (vertex, angle start, then end points) and Offset (a distance or Through, then a line, construction line or ray, then a side or point). **RAY** (`RAY`): a start point, then through points. Each line is one undo step. Move, Copy, Rotate, Mirror, Scale, Stretch (by base point), Offset (to a side) and Properties (Base X, Y and Angle) work; they snap as Endpoint (a ray's base) and through intersections, nearest and perpendicular with other objects, and are boundaries for Trim and Extend. **FILLET and CHAMFER** work on them (`od-core/src/corner_infinite.rs`: each stands in as a very long line, and the result is turned back, so a construction line cut at one end is a ray, a ray stays a ray, and one cut at both ends is a line; zero radius or distance makes rays meet at the corner). TRIM and BREAK work on them (cut as the long line that stands for them, `Entity::long_line` and `Entity::resumed`: a construction line cut once is two rays, cut twice it is two rays and a line between, BREAK of a ray leaves a line and a ray). Extend does not apply (they have no end to reach) and AutoCAD's JOIN refuses them too. As cutting edges and boundaries they already worked. A window selects one never; a crossing window or a click does. DXF reads and writes `XLINE` and `RAY` (R2000); the API shows them read-only (writing them is a separate change). Grips: the base point moves the line and a grip 80 pixels along it (two for a construction line, one each way) turns it about the base; the pixel size is passed in with `infinite::set_pixel_size`, which the canvas sets every frame. A linetype shows on screen and when plotted, laid from the base point so it does not move as the view does (the plot cuts the line to the viewport first). BOUNDARY treats them as lines across the drawing. **Not done:** construction lines in blocks (the table refuses them: they have no size to give a block).

## Boundary (done 23-10-2026)

## Release pipeline (phase 1 of the release and update plan, 24-10-2026)
`.github/workflows/release.yml` is now `verify` (the tag must be `v` plus the `Cargo.toml` version and its commit must be on `main`; a version with a `-suffix` is a prerelease), `check` (fmt, clippy and tests on Windows and Ubuntu 22.04), `package` (`scripts/package.sh` on each system) and `publish` (tag only: checksums, a draft release with every file, then made public). ## PEDIT (done 23-10-2026)
`PEDIT` (`PE`; Home > Modify flyout, "Edit Polyline"). Code: `pedit_cmd.rs` (the menus), `pedit_join.rs`, `pedit_vertex.rs`, `pedit_memory.rs` (`PEDITACCEPT` and the Join type, saved with the user's settings), `properties/polyline.rs`; the pure edits are methods of `PolyData`, the four lists of a polyline, in `od-core/pedit.rs` with `pedit/join.rs` and `pedit/vertex.rs`; `od-core/polyline.rs` holds the validity check and limits. Pick one object, or use a selection of one; several selected objects, or the Multiple option, edit all at once. A pick or preselection that is no polyline is refused (a spline by name) and the pick prompt stays. A line or arc asks "turn it into one?" (Yes by default; `PEDITACCEPT` 1 skips the question); a rectangle converts without asking, as it is a polyline in AutoCAD; Multiple asks once whether to convert lines, arcs and rectangles. Options: Close/Open (whichever applies), Join, Width, Edit vertex, Decurve, Ltype gen (ON/OFF: the object's `continuous_generation` flag, which the canvas, plot and DXF already honour), Reverse, Undo (takes back the last change made in this command, the conversion included). Each change is one undo step. Menus are `Wants::Keyword` prompts (`Editor::ask_keyword`), so typed letters pick keywords and Enter finishes.
- **Join** takes a selection of lines, arcs and open polylines whose ends meet the polyline's and chains them on, the nearest ends first (ties go to the tail of the chain, then selection order), either end, either direction, keeping each piece's bulges and widths (a line or arc joins hairline). Ends count as one point within a tolerance that grows with the size of the coordinates. At most 10,000 candidates. Objects on locked layers or in another space (layout) than the polyline are left out. It reports "n segments added to polyline." and, when joined objects had other layer, colour and so on, how many lost them. Closed polylines neither join nor are joined to. Single-object Join joins only ends that meet. **Multiple** asks "Enter fuzz distance or [Jointype]": within the fuzz, Extend moves both ends to where their lines cross (extending or trimming; only straight end segments, and the crossing must lie within the fuzz of both ends), Add bridges the gap with a straight segment, Both tries Extend then Add. The type is remembered (default Extend, as AutoCAD's). Associative hatches and dimensions follow a joined or edited polyline in the same undo step (tested).
- **Width** sets every segment; **Decurve** drops all bulges (AutoCAD's also removes fit-curve vertices; we have none); **Reverse** turns the path round, curves and widths with it.
- **Edit vertex**: a cross, six screen points to an arm whatever the zoom (`Options::marker`, drawn by the canvas), marks the vertex; Next, Previous (Enter is Next; they stop at the ends and do not wrap, as in AutoCAD), Insert (a vertex after the marked one: on a straight segment exactly where given, on an arc the nearest point of the arc, which splits it into two arcs of the same circle; the width tapers by distance along the segment), Move, Regen (does nothing), Straighten (pick a second vertex with Next/Previous/Go: the vertices between go and one straight segment is left), Break (the same pick: the stretch between is removed, leaving two polylines, or one when closed or cut at one vertex; the second is a new object on the same layer; vertex editing then ends, which AutoCAD's documentation leaves open) and Width (start and end width of the next segment), eXit.
- **Properties** shows Vertices, Closed (typed over: Yes or No), Global width (typed over; Varies when the segments differ) beside Length and Area; Linetype generation was already a row.
- **Validity**: `Document::validate` (and block definitions) refuse a polyline with fewer than two vertices, non-finite points, bulges or widths not one per vertex, a non-finite or huge bulge (over 1e12), or a negative, non-finite or huge width (these limits are ours, not AutoCAD's).
- Checked in the built exe (23-10-2026): drawing a polyline, selecting it, the Properties rows, PEDIT with the selection, typing E and N at the menus, and the vertex cross at its place. That run found two bugs the tests had missed (typed keywords were taken as text, and the option list showed twice); both are fixed and covered by a test that types.
**Not done:** Fit, Spline (AutoCAD's curve fitting of a polyline; a Spline pick is refused by name), vertex Tangent, spline conversion with `PLINECONVERTMODE` and its precision. All need AutoCAD output to match; so do the DXF items from `private_material/pedit_command_specification.md`: reader limits and the vertex-count check, structured import warnings, and golden fixtures from AutoCAD. Joining splines and ellipses. Extend does not handle arc end segments. In Multiple, Close and Open are separate keywords.

## Home page v2, slice 4b: previews on Home (done 23-10-2026)
Recent drawings are cards by default (two columns from 540 px of content, else one; List keeps the rows, the choice is saved in the recent list's JSON as `view`). A card: the picture over name, folder, age and size, a format badge (ODX, DXF, DWG), an Open badge, a pin mark when pinned, and the Pin and More buttons, sharing `home_page/controls.rs` with the rows; a missing file's picture is dimmed and marked. Without a picture the card shows a quiet grid with the format named.

**How a picture is made.** `previews.rs`: after a drawing has read (open or import, unless a picture of the file as it is already exists) or been written (save), the I/O job hands a copy of the document to one preview worker thread, which renders it with `od_canvas::preview`, encodes a PNG (`png` 0.18.1, MIT OR Apache-2.0, already in the lock file through egui's `image`; 8-bit RGB, High compression, over 150 KB is not kept), reads the file's date and length at that moment (so a save is keyed by what it wrote), and stores it atomically (temporary file, then rename) as `<fnv64 of renderer version, real path, modified ms, length>.png` in `previews/` beside the settings. A failed or panicking render never fails the open or save. Nothing is loaded just to be pictured. Another program changing a file changes its key, so the old picture stops matching and is not shown. `RENDERER_VERSION` (now 2) must be bumped when the renderer's output changes on purpose.

**How it is shown.** `preview_textures.rs` keeps a texture per recent record, loaded by the same worker (no disk read or decode on the UI thread), at most 16 (10 MiB) and only for the first 16 entries. A save keeps the entry's old picture on screen until the new one is read (no flash); an outside edit drops it at once; a failed render shows the placeholder. The pending test is taken before the worker's reports are read, and a report is sent before its path stops being pending, so there is no gap in between (a test covers it).

**Budgets, measured** with `cargo run --release -p od-app --example preview_bench` (set `OD_PREVIEW_OUT` to keep the pictures) on the sample drawings and three big site drawings: render 0.2 to 36 ms (12,000 to 16,000 objects: 13 to 36 ms), PNG 1 to 42 KB. Disk: at most 64 pictures and 16 MiB, oldest first (about 3 MB at these sizes). First-Home-frame time was not measured before and after.

**Differences from the spec.** The picture is black-on-white like a plot, not the dark drawing background (a plot turns white lines black; dark paper would hide them). It fits the drawing's extents less strays (`preview::content_bounds`: with 50 objects or more, objects well outside the middle 96% of centres are left out of the fit), because one stray object made a real site plan a speck. The cache index is the file names themselves (the key is in the name), so there is no index file. Not done: a skeleton while loading (the placeholder serves), blocks and text in the pixel-hash fixtures, Linux.

## Home page v2, slice 6: templates (done 23-10-2026)
Decisions (from James): a template is a separate `.odt` file, and there is one user templates folder.

**The file.** `od-files/src/template.rs`: `TemplateFormat` (`.odt`, "OpenDraft template") reads and writes exactly what `.odx` does, so it needs no format version of its own; it is in `FORMATS`, so Open lists it and a template can be opened and edited as a drawing (Save then writes the `.odt`; Save As gives an `.odx`). `template_path`, `is_template` and `template_filter` follow `native_path` and `native_filter`.

**Where.** `templates/` beside the settings (`AppState::templates_dir`), made when first saved to. Starters built into the program (`templates.rs`: Blank millimetres, inches, and feet and inches, which set the units and nothing else) are listed apart from the user's own.

**Making one.** `Save as Template...` (command `file.save_template`, alias `SAVEASTEMPLATE` or `TEMPLATE`, in the application menu) writes a copy of the active drawing as `.odt`, starting in the templates folder; the drawing itself is untouched. Not given to automation (`Denied`, `FileWrite`, as Export DXF).

**Using one.** Home has `Template...` beside Open... and a Start section (Blank drawing, From template...) above Handy keys. Both open the picker (`app/template_dialog.rs`): Starters, then Your templates, each with its name over what it sets up (length format and unit, "model space only" or the layout count, layers); the folder is read on a worker when the picker opens (a "Looking..." line meanwhile). Picking one calls `AppState::new_from_template`: a starter at once, a file read on the worker (`Done::FromTemplate`); the result is a new untitled `DrawingN` with no file that counts as unchanged until edited (and replaces a blank untouched drawing), so Save asks for a name and the template is only ever read. ## Measuring: DIST and AREA (done 25-10-2026)
`inquiry.distance` (DI, DIST) and `inquiry.area` (AA, AREA) are the first two items of the Utilities > Measure dropdown; Radius, Angle and Volume stay on the not-built list (`ribbon_def/home.rs`). They change nothing in the drawing and answer on the command line, in the drawing's units (`measure_cmd.rs`). The maths is pure and tested in `od-core/src/measure.rs`: `Entity::measured` (length, closed or not, area), `corners` (area and perimeter of corner points) and `separation` (distance, angle, offsets).

**DIST:** first point, second point (a rubber band and live distance/angle boxes), then `Distance = 5.0000, Angle in XY Plane = 53` and `Delta X = 3.0000, Delta Y = 4.0000`. The Multiple points option adds up a path: each step and the running total, Undo to take back a point, Enter for `Total distance`. No Z (the drawing is 2D), and no DISTANCE system variable yet.

**AREA:** corner points (a ghost of the shape) with Enter for the total, or Object. Add area and Subtract area keep a running total across shapes (`Total area = ...`, eXit to leave). Objects: circle, rectangle, closed or open polyline (arcs included; an open one is closed by a straight line for the area, and reports `Length`), ellipse, spline. A line or an arc reports only its length and says it encloses no area. Areas are plain numbers at the length precision (`format_area`, now also used by the Properties panel).

**Not done:** Radius, Angle and the MEASUREGEOM wrapper (`MEA`), hatch and region areas, hatch/object selection by area (the AREA Object option picks one object only), the DISTANCE, AREA and PERIMETER system variables, Arc and Length options in Distance Multiple points, and area units such as square feet from feet-and-inches drawings. Not yet tried by hand in the app: the tests drive the commands with `AppState`.

## Overkill (done 26-10-2026; brought to AutoCAD parity the same day)
`OVERKILL` (`overkill_cmd.rs`; maths in `od-core/src/overkill/`: `mod.rs` the engine and settings, `equal.rs`, `merge.rs`, `polyline.rs`; dialog `app/overkill_dialog.rs`): select objects (or use the selection), then AutoCAD's Object Comparison Settings dialog opens (a `Wants::OverkillDialog` prompt carrying `overkill::Settings`, answered by `Reply::Overkill`, like the MTEXT editor); OK runs it, Cancel cancels. The dialog has Tolerance (default 1e-6; zero asks for an exact match), Ignore (Color, Layer, Linetype, Linetype scale, Lineweight; Thickness, Transparency, Plot style and Material are shown switched off, as OpenDraft has none), and the options Optimize segments within polylines (its width and do-not-break sub-options shown off), Combine co-linear objects that partially overlap, Combine co-linear objects when aligned end to end, and Maintain associative objects (all on). The last settings are offered again and saved with the user's settings (`overkill_memory.rs`). `-OVERKILL` (`overkill_line.rs`) loops on `Enter an option [Ignore/Tolerance/Optimize polylines/Combine partial overlap/combine End to end/Associativity] <accept>` over the same settings and `run`.
What it does: exact duplicates go (lines either way round, circles, arcs, rectangles, points, polylines from any start point and either way round, with their bulges and tapers mirrored properly); a line or arc wholly on another goes; collinear lines and arcs of one circle that overlap in part or meet end to end become one (arcs that close the circle become a circle; a circle swallows arcs of itself); optimising drops repeated vertices and the middle vertex of a straight run (not where there are widths or curves). Objects compare only within the same layout and the same layer, colour, linetype, linetype scale and lineweight unless ignored; objects on locked or hidden layers are left alone and counted. With Maintain associative objects on, anything an associative hatch, a dimension or a leader is tied to is never deleted or changed (its duplicates still go, and lines lying on it). A bad tolerance, more than 100,000 objects or more than 25,000,000 comparisons stop it with a message and no change. The first of a group keeps its place; one bulk change and one undo step.
**Not done:** comparing polyline segments with standalone lines and arcs and splitting polylines (so AutoCAD's width and do-not-break options), redirecting associations to the survivor instead of protecting (Maintain associative objects off just frees them), the properties OpenDraft lacks, a ribbon button and icon (AutoCAD keeps OVERKILL in Express Tools), AutoCAD conformance fixtures, driving it in the real app.

## Purge (done 26-10-2026; brought to AutoCAD parity the same day)
`PURGE` (`PU`; Insert > Block > Purge) opens a two-page dialog laid out like AutoCAD's (`app/purge_dialog.rs`, the tree in `app/purge_dialog/purge_tree.rs`): two big page buttons, the tree on the left, Preview and Options on the right, and Purge Checked Items, Purge All and Close underneath. **Purgeable items** is a tree (an All items root and every kind AutoCAD lists, each with a three-state checkbox; the kinds OpenDraft has no table of are shown switched off), nothing ticked to start with, of the named items nothing uses (blocks, dimension styles, layers, linetypes, multileader styles, text styles); clicking a name pictures it in the Preview pane (blocks only; `block_picture` draws the definition alone); **Find non-purgeable items** lists the rest with every reason each stays (current, permanent, used by N objects, inside a block, by a style that stays, frozen in a viewport) and a Select Objects button that selects the objects using it (`od_core::purge::{blocked, users_of}`). In the Options pane, **Purge Unnamed Objects** holds separate, unticked options with counts: zero-length geometry (exactly zero length: lines, arcs, circles, polylines; a full-circle arc is not) and empty text, and a switched-off Orphaned data; objects on locked layers are never offered. **Confirm each item to be purged** (off) asks on the command line `Purge block "X"? [Yes/No/All]` while the dialog steps aside; **Purge nested items** (on) goes on to what deleting frees, round after round on a copy of the drawing, with no depth limit (every round deletes something, so it ends). The four switches are saved with the user's settings (`purge_memory.rs`). Purge deletes the ticked items, Purge All every named item (plus the unnamed options switched on), Close leaves; all questions come first, the deleting is one undo step (`purge_cmd.rs`, `purge_delete.rs`), and a drawing that fails `validate` is refused.
`-PURGE` (`-PU`; `purge_line.rs`) follows AutoCAD: `Enter type of unused objects to purge [Blocks/Dimstyles/LAyers/LTypes/MUltileaderstyles/textSTyles/Zero-length geometry/Empty text objects/All]`, then `Enter name(s) to purge <*>` (comma-separated, `*` and `?` wildcards; a name that cannot go is explained), then `Verify each name to be purged? [Yes/No] <Yes>`, and removes one level (run it again for what that freed); All covers the named kinds only. AutoCAD's other kinds (groups, materials, plot styles, shapes, multiline, table, visual and detail view styles, registered applications, orphaned DGN data) are accepted and answered "OpenDraft does not store them".
What is never offered: layer 0, the current layer, `Standard` styles, the current dimension, multileader and text styles, `Continuous`, `ByLayer`, `ByBlock` and the linetype new objects use, anything an object, a block definition, a layer or a style that stays refers to, a layer frozen in any viewport. A new drawing's stock linetypes (DASHED, DOT...) count as unused, as in AutoCAD; load them again from the Linetype Manager.
**Not done:** a confirmation window in place of the command-line questions, previews of anything but blocks (linetype patterns, text samples), category icons, Help, AutoCAD's other kinds (no tables to purge), anonymous blocks, AutoCAD conformance fixtures, driving it in the real app.

## MTEXT editor box: resize grips and one box everywhere (done 26-10-2026)
The text's box is now one thing: `MText::reference_height` (0 = as tall as the text) sits beside `reference_width`, and `frame_height = max(text height, reference_height)`, so the box dragged out with MTEXT, the selection frame and hit test, the grips, bounds and snaps, and the in-place editor all use the same rectangle. The editor has grips as in AutoCAD (`mtext_editor/box_handles.rs`: right edge = width, bottom = height, corner = both) and a selected text has the same three beside its move grip (`MText::grips`, `with_grip_moved`; the edge dragged moves, the opposite one stays, whatever the attachment). The height is saved in `.odx` (optional `box_height`, no version bump), scaled with the text, and is never less than the text. Before, the editor drew a box exactly as tall as its text. Only the area the text fills is picked, so other objects drawn in the empty part of a bigger box can still be selected (window and crossing selection use the whole box). **Not done:** DXF and DWG do not carry it (a reopened DXF text is as tall as its content; AutoCAD's own codes for it, 43 and 46, are not written), the Properties panel has no height field, the API (`od-api`) does not show it, and resize cursors do not follow rotated text.
